# Architecture

## Modules

Each module is a CMake target usable on its own, with its own tests, guide and example, and depends only on the modules under it.

| Module | What it does | Built on |
|---|---|---|
| core | UTF-8 text helpers over `std::string`, paths over `std::filesystem`, values with JSON, XML documents, speaker layouts, the message loop and timers, threads, spin locks, lock-free FIFOs, logging, settings files written safely, SHA-256 | C++20, CHOC |
| files | Reading and writing audio files: WAV with BWF and iXML and RF64, AIFF, FLAC, Ogg Vorbis, Opus; reading MP3; AAC, M4A and CAF through the system's own decoders; streaming readers for files of any length; a writer an audio device's thread records through | CHOC, AudioToolbox, Media Foundation |
| devices | Audio and MIDI devices: Core Audio, Windows Audio in shared and exclusive mode, ASIO with the developer's own SDK, ALSA, PipeWire and JACK; device lists and changes, latency in and out, inputs and outputs run apart or together | System APIs, CHOC's device layer where it fits |
| ui | The system's web view (WKWebView, WebView2, WebKitGTK) with a typed bridge: native functions the page calls and awaits, events the native side sends, and resources served from memory; windows, native menus, dialogs, file choosers, drag and drop, the clipboard, keyboard handling | CHOC's web view, AppKit, Win32, GTK |
| app | A desktop application around it: one instance or many, worker processes with a message channel, opening files from the system, updates' hooks | core, ui |
| plugin | Plugins written once against a CLAP-shaped C++ interface (parameters, state, buses, latency, processing, an editor as a web page) and built as CLAP, VST3, AU v2 and v3, AAX and standalone | CLAP, clap-wrapper, VST3 SDK, AudioUnitSDK, the developer's AAX SDK |
| host | Hosting other makers' plugins: VST3, AU v2 and v3, CLAP; scanning in worker processes; a plugin made in the background or at once, on the message thread or out of process for AU v3; buses, state, parameters, latency, offline rendering, and its editor in a window | VST3 SDK, AudioToolbox, CLAP |

## Layout and conventions

Each module lives in `Modules/<name>`: its public headers in `include/symbolengine/<name>/`, with `symbolengine/<name>.h` including them all, its sources in `src`, and its tests in `Tests`. It builds as the static library `SymbolEngine::<name>`. Everything is in the namespace `symbolengine`, classes at its top and groups of functions in namespaces of their own, such as `symbolengine::json`, `symbolengine::paths` and `symbolengine::files`.

Text is UTF-8 in `std::string`, and paths are `std::filesystem::path`, turned to and from UTF-8 with `paths::fromUtf8` and `paths::toUtf8`, since a path's own `string()` uses the system's code page on Windows. Text written for files and for other programs, numbers included, comes out the same on every system and in every locale. A function that can fail for reasons outside the program, such as a missing file, throws `std::filesystem::filesystem_error` or, given a `std::error_code`, sets it, as `std::filesystem` does. Reading data that may not be there, such as a member of a parsed value, never throws.

Values hold what JSON holds, keeping whole numbers as 64-bit integers so that sample positions stay exact, and objects keep their members in the order they were added. JSON is written as browsers write it, so a page and the native side read each other's numbers exactly. Files that hold a user's work or settings are written beside the old one and moved into its place in one step, so a crash leaves either the old file or the new one whole, and a settings file that can't be read is kept aside instead of being overwritten.

XML is read and written for documents of data, such as settings, lists and session files: elements with their attributes in order, the elements inside them and their text. The entities XML defines and character references are read, and a document's own entities never are, so a document can't make itself grow without bound. Everything written reads back as it was, line breaks in attributes included.

## Web pages

A page is served from files built into the program with `symbolengine_add_files`, by path from `/index.html`, and every page is also served `symbolengine.js`, its side of the bridge: `symbolengine.call` reaches a native function the program exposed and gives what it returned, or the message of what it threw, or waits for an answer the function gives later, as after a dialog, and `symbolengine.on` receives the events the program sends. Values cross as JSON, so a page and the native side read each other's numbers and text exactly. Some systems start loading a page before the web view says it is ready, so the bridge waits for the native side before its first call, and the native side holds what it sends until the page has said it is listening; nothing sent early is lost on any system. A page's name becomes its address, so pages with different names keep what they store apart even in one program; a plugin's editor is named after the plugin's id, so two plugins in one host never read or overwrite each other's stored data. On Windows each program, or each plugin, also gives WebView2 a data folder of its own; CHOC has no setting for one, so the build adds it to CHOC's web view when it fetches it (`cmake/PatchChoc.cmake`), with a second change that passes the keyboard on to the page when its window is given it, as a Mac's web view takes it, and stops if CHOC's code has changed under the patch. Linux's web view, WebKitGTK, follows the first release.

A program's own window, `ui::Window`, has the system's title bar and holds one native view, such as a web view, which fills it and is given the keyboard with the window. Its size is in points on a Mac and in pixels at 100% on Windows, which it scales to the screen it is on, so it looks the same size on each; its place on the screens, kept between launches, is held to a screen it can be reached on when it opens. Its close button only tells the program, which hides or destroys it, and it can stay see-through while its page draws its first frame, light or dark as the computer or the program says.

## Audio files

The files module reads and writes audio files a stretch at a time, so a file of any length takes little memory, with each channel's samples as floats. A whole number reads as itself divided by 2 to the power of one less than its bits, so a 16-bit sample is divided by 32768, and writes back as the same number; a float is written as the nearest whole number to it times that, held within the format's range, and anything that isn't a number as silence. Float files keep their floats as they are, past full scale too. A file is recognized by what it holds, never its name.

WAV is read whether it says its sizes in RIFF's 32 bits or in RF64's and BW64's ds64 chunk, its sample format plain or in WAVE_FORMAT_EXTENSIBLE, whose speakers it gives. A WAV is written with a JUNK chunk where a ds64 chunk fits, so it becomes RF64 in place when it passes 4 GB; as plain PCM up to two channels, floats with a fact chunk, and WAVE_FORMAT_EXTENSIBLE for more channels or speakers given. AIFF and AIFF-C are read with their samples in either byte order or as floats, and written as AIFF, or AIFF-C for floats. A file's other chunks, such as a broadcast extension, iXML, cue points and LIST, are kept as they are and written back the same, so a recording's details survive an edit; a broadcast extension also reads and writes field by field. A file whose writing was stopped, or that says more than it holds, reads up to its last whole frame, and a chunk of odd length is read whether its pad byte is there or not.

A WAV or AIFF being written can be flushed: its header is rewritten for the samples so far and the system puts it on disk, so a recording stopped by a crash reads to there, and a WAV past 4 GB becomes RF64 then. `BackgroundAudioWriter` writes a file from a thread that mustn't wait, such as an audio device's: that thread copies its samples into a buffer, never locking, waiting or allocating, and the writer's own thread writes them, flushes the file every second or the interval given, and gives each stretch, as the file holds it, to whatever draws or measures the recording. A stretch the buffer has no room for is refused whole, so the recording can say what it lost.

FLAC, Ogg Vorbis and Opus are read and written through Xiph.Org's own libraries, libFLAC, libvorbis with libogg, and opusfile and libopusenc over libopus, compiled from their sources into the files module with their processor-specific code left out, so they build alike everywhere, and every function of theirs hidden inside whatever links them, so two plugins in one host never meet. libvorbis comes from after its last release, 1.3.7, for the fixes made since, one of them to a use-after-free in seeking, and its encoder's leak in setting up 5.1 is mended in a copy of the one file that has it. Their tags are Vorbis comments, read and written as names and values. FLAC is written in 16 or 24 bits, its length and MD5 signature filled in once the samples are all in, with room left to change its tags later; Ogg Vorbis at a quality and Opus at a bit rate. Channels are always in WAV's order, Ogg Vorbis' and Opus' own turned to it as they are read and written. Opus plays at 48 kHz whatever rate it was made from, with the encoder's start-up samples left out, and a stretch read after a jump is decoded from half a second before, as Opus' decoder settles slowly, so it reads exactly as it does when the file is read through.

MP3 is read through minimp3, built in and hidden the same way, exactly to the sample wherever a read starts. A file whose first frame holds LAME's or Xing's information reads without the samples its encoder and decoder put before the audio and the padding after it, as gapless players read it, so the audio lies where it lay before it was encoded; a file without that information reads as it decodes. M4A and other MPEG-4 audio, AAC in ADTS and CAF are read by the system's own decoders, which come with the system and its licenses: AudioToolbox on a Mac, which reads all three, and a WAV or AIFF-C whose samples are coded in a way of their own, such as ADPCM or µ-law, and Media Foundation on Windows, which reads M4A and AAC. Media Foundation reads Windows Media's WMA too, and on a Mac a file of any other kind goes to AudioToolbox, which reads AC-3, AMR, Sun's AU and more, so the files module reads what each system's own players do; `files::readableExtensions()` lists them, for open dialogs. Media Foundation is loaded when a file first needs it, so a Windows without it, as its N editions are, finds those files unsupported and runs everything else, and no thread's COM is started or changed. AAC's priming samples are left out where the file says how many there are, in its edit list or iTunes' iTunSMPB; Media Foundation acts on the edit list alone, so on Windows the files module reads iTunSMPB itself, as Apple's encoder writes it. Channels come in WAV's order. On Windows a stretch read after a jump is decoded from half a second before, so it reads exactly as it does when the file is read through. Linux reads these after the first release.

The reader is checked against files written by other programs, ffmpeg's, Apple's, LAME's and the flac tool's, sample for sample where the format is lossless and by each channel's tone where it isn't, and what it writes is read back by them in the same way.

## Threads and real time

Three kinds of thread, named in every interface: the message thread, which owns windows, web views and plugin editors; the audio thread, which never allocates, locks or waits, and is checked for it in debug builds; and worker threads for everything slow. Every callback says which thread it is on. Nothing is a global singleton the user didn't make; a program creates its message loop, devices and hosts and passes them where they are needed.

## Interfaces

A plugin's editor and an app's screens are web pages in the system's web view, loaded from resources built into the binary; meters and spectrograms drawn this way run at 60 frames a second. The bridge is typed both ways, its native functions and events declared once and checked on both sides. A native drawing surface for interfaces that can't be web pages is a later question, not a starting point.

## Plugins

A plugin is a class derived from `Plugin`, written once, whose static `describe()` gives its id, name, vendor and features. Its constructor adds its parameters, each with an id kept forever, a range, a default, and text for showing and typing its values; decibels, numbers with units, choices, switches and a bypass come ready-made, and so do parameters hosts see and record from 0 to 1 on a linear scale or one even by ratio, as frequency and Q are heard, shown and typed in their own units, which is how plugins already released with such parameters keep the automation their users recorded. Its buses are stereo in and out unless it says otherwise, and it says which layouts it takes: any standard one from mono to Dolby's 9.1.6 and the ITU 9.1.6, each channel named by its speaker, or one of its own. CLAP has no numbers for the wide pair of Dolby's 9.1.4 and 9.1.6, so those two pass only between a plugin and the fork's VST3 and Audio Unit wrappers below, which say so with an extension of the fork's own, and a CLAP host is never given them. A host asks for a layout by its speakers or by its channel count alone, which gives the first standard layout with that many channels the plugin takes, and is told which speaker each channel is for. A plugin is given its channels in the same order in every format, the order of the speakers' numbers, which is VST3's: an Audio Unit host's layout in another order, such as Atmos 7.1.4 with its side pair before its rear pair, is handed over rearranged, which copies nothing. A speaker arrangement a plugin refuses in VST3 stays refused, instead of being asked for again by its channel count, which would leave the host naming the channels for speakers the plugin isn't feeding. The framework keeps each parameter's value where the audio thread reads it without locking, splits each block where the host changes a parameter so that automation is exact to the sample, flushes denormal numbers to zero while the plugin processes, and saves and loads the parameters as JSON unless the plugin saves more. A plugin hears when the host renders offline, so it can take as long as it needs, and tells the host when its state changes outside its parameters, so the host asks to save. An exception thrown in a plugin's code fails the host's call instead of crashing the host.

A plugin's editor is a web page in the host's window, on Mac and Windows, its files built into the plugin. The page is served `plugin.js` beside `symbolengine.js`, which gives it each parameter with its name, range, value and text, and its steps for a choice; it calls a handler whenever the value changes, whether the page, the host's automation or a preset changed it, and sets values in gestures, which the host hears as the begin, value and end events it records automation from: through `process()` while the plugin is processing, and by asking the host to flush them while it isn't. About 30 times a second, or as often as up to 120 when the plugin asks, it may send the page what it measures, such as levels, without the audio thread waiting on anything, and its own functions the page calls can change parameters in gestures as the page does, which the host records the same way. A Mac host sizes an editor in points and a Windows host in pixels, telling the plugin how many pixels a point is.

A resizable editor is held to its limits, and the page can ask the host for a size with `plugin.resize`. It opens at its instance's own size, or the size the user last gave an editor of that plugin, kept in a file once a resizing has rested for 0.6 s, or the size the plugin gives; all fitted to the screen it opens on. The plugin hears of each new size, to keep it in its own state, and can set the size its editor opens at. For checks run from a script, an editor saves a picture of itself when `SYMBOLENGINE_EDITOR_SNAPSHOT` names a PNG, after running `SYMBOLENGINE_EDITOR_SCRIPT` in the page; on a Mac for now. In a debug build, `SYMBOLENGINE_LIVE_FILES=1` reads every page's files from the folders they were built from, so a page is changed and reloaded without building again, and the source folders' paths never reach a release build.

A plugin binary lists its plugins with `SYMBOLENGINE_PLUGINS`, and `symbolengine_add_plugin` in CMake builds it as CLAP, VST3 and Audio Units. Every format is built through CLAP, and clap-wrapper turns the CLAP build into each other format, so a fix lands in every format at once. SymbolEngine builds with its own fork of clap-wrapper, at github.com/cybra/clap-wrapper, whose symbolengine branch adds SymbolEngine's changes to a clap-wrapper release, each a commit of its own: the speaker arrangements above for VST3, channel layouts for Audio Units, where the layouts a plugin takes are offered to the host, Logic's channel orders among them, the wide pair in both, and a value the host sets in an Audio Unit kept in the state it saves straight after, with no render between, as hosts expect of an Audio Unit. The VST3 SDK and Apple's AudioUnitSDK are fetched, pinned by checksum, only when a plugin is built in a format that needs them. Nothing in a plugin is visible outside it but its entry point, so plugins built on different versions of SymbolEngine load side by side in one host.

Every plugin built in the repository is checked in continuous integration: loaded from its binary as a host loads it, made, run and destroyed, on every system and in the sanitizer build, which builds plugins as CLAP alone; by CLAP's validator and Steinberg's VST3 validator on Mac, Windows and Linux; by pluginval, run as a separate tool, at its strictest level; and by Apple's auval on the Mac.

## Moving an existing plugin

A plugin that already ships keeps what hosts and its users have of it. It states its own identity, the VST3 class ID in its description and the Audio Unit type, subtype and manufacturer codes in `symbolengine_add_plugin`, as it was released with them, which clap-wrapper passes to each format, so a DAW session finds it. A test plugin states a class ID, and Steinberg's validator finds it under that ID on every system. It receives the state its earlier versions saved, exactly as the host stored it, so it can open presets and sessions with their settings: a VST3 host's bytes as they are, and an Audio Unit's from under the key its earlier versions kept it under, `AU_STATE_KEY` in `symbolengine_add_plugin`, where it also saves it, so earlier versions open its sessions too. It keeps the parameter numbers hosts recorded automation against.

## Hosting

Plugins are scanned in worker processes, one plugin at a time per worker, so a plugin that crashes or hangs fails alone; a worker that loses its link to the host ends at once. What was found and what failed are kept, so a scan looks only at what is new, and a scan cut short carries on next time. A plugin is made with stereo in and out where it takes them, and one that describes its buses only once an arrangement is set on them is given stereo first, as a DAW does. A plugin with no audio out is set aside with a reason instead of silencing what plays through it. Its editor opens in a window kept above the app's, which steps back while the app asks a question, and Space reaches the app's transport even when the plugin's view takes every key, unless text is being typed. Each of these comes from a real plugin and has a test.

## Devices

Lessons from recording on real devices are built in: an input runs apart from the output when the two can't share a pace; a shared-mode Windows input asks for a long enough buffer and passes on what built up after a late turn; a take records the time the computer slept or the device dropped out, and says so; latency in and out is measured, not only reported, so recordings line up.

## Testing

Unit tests for every module, the plugin validators on every example, and integration tests that open real devices where the runner has them. Continuous integration builds and tests on Mac, Windows and Linux on every push, with warnings as errors; on the Mac for Apple Silicon and Intel together, and on Linux a second time with the address and undefined-behavior sanitizers. On each run a project outside SymbolEngine builds against it both ways a project takes it in, by FetchContent and by find_package after installing. Symbol Studio's own checks, run against each release, are the proof that the parts work together in a real product.

## Dependencies

Only permissive licenses: MIT, ISC, BSD, zlib, Boost and Apache 2.0, each fetched by CMake and pinned by checksum. SDKs under other terms, AAX and ASIO, are supplied by the developer and never included.
