# Architecture

## Modules

Each module is a CMake target usable on its own, with its own tests, guide and example, and depends only on the modules under it.

| Module | What it does | Built on |
|---|---|---|
| core | UTF-8 text helpers over `std::string`, paths over `std::filesystem`, values with JSON, XML documents, gzip, files read through memory, speaker layouts, lock-free FIFOs, a resampler, child processes and the link to them, settings files written safely, SHA-256 | C++20 |
| files | Reading and writing audio files: WAV with BWF and iXML and RF64, AIFF, FLAC, Ogg Vorbis, Opus; reading MP3; AAC, M4A and CAF through the system's own decoders; streaming readers for files of any length; a writer an audio device's thread records through | CHOC, AudioToolbox, Media Foundation |
| devices | Audio and MIDI devices: Core Audio, Windows Audio in shared and exclusive mode, ASIO with the developer's own SDK, ALSA, PipeWire and JACK; device lists and changes, choosing and restoring devices, latency in and out, an input and an output on clocks of their own, files played through a device with a read-ahead | Core Audio, Windows Audio, the developer's ASIO SDK |
| net | Fetching from web servers through the system's own client, NSURLSession on a Mac and WinHTTP on Windows, its certificates, proxies and redirects, each piece of an answer handed over as it arrives; addresses for files | core, the system's client |
| ui | The message loop and timers; the system's web view (WKWebView, WebView2, WebKitGTK) with a typed bridge: native functions the page calls and awaits, events the native side sends, and resources served from memory; windows, native menus, dialogs, file choosers, drag and drop, the clipboard, keyboard handling | CHOC's web view and message loop, AppKit, Win32, GTK |
| app | A desktop application around it: the system's application object and what it asks of a running program, one instance or many, worker processes with a message channel, opening files from the system, updates' hooks | core, ui |
| plugin | Plugins written once against a CLAP-shaped C++ interface (parameters, state, buses, latency, processing, an editor as a web page) and built as CLAP, VST3, AU v2 and v3, AAX and standalone | CLAP, clap-wrapper, VST3 SDK, AudioUnitSDK, the developer's AAX SDK |
| host | Hosting other makers' plugins: VST3 and Audio Units v2 first, Audio Units v3 and CLAP after; scanning in worker processes that prove what each plugin will do; a list of plugins by their full identity; each plugin's life on the main thread and its processing on the audio thread; buses, parameters, state, latency and delay compensation, copies for offline rendering; editors in the program's windows, and a page of parameters for a plugin with none | VST3 SDK, AudioToolbox, CLAP |

## Layout and conventions

Each module lives in `Modules/<name>`: its public headers in `include/symbolengine/<name>/`, with `symbolengine/<name>.h` including them all, its sources in `src`, and its tests in `Tests`. It builds as the static library `SymbolEngine::<name>`. Everything is in the namespace `symbolengine`, classes at its top and groups of functions in namespaces of their own, such as `symbolengine::json`, `symbolengine::paths` and `symbolengine::files`.

Text is UTF-8 in `std::string`, and paths are `std::filesystem::path`, turned to and from UTF-8 with `paths::fromUtf8` and `paths::toUtf8`, since a path's own `string()` uses the system's code page on Windows. Text written for files and for other programs, numbers included, comes out the same on every system and in every locale. A function that can fail for reasons outside the program, such as a missing file, throws `std::filesystem::filesystem_error` or, given a `std::error_code`, sets it, as `std::filesystem` does. Reading data that may not be there, such as a member of a parsed value, never throws.

Values hold what JSON holds, keeping whole numbers as 64-bit integers so that sample positions stay exact, and objects keep their members in the order they were added. JSON is written as browsers write it, so a page and the native side read each other's numbers exactly. Files that hold a user's work or settings are written beside the old one and moved into its place in one step, so a crash leaves either the old file or the new one whole, and a settings file that can't be read is kept aside instead of being overwritten.

XML is read and written for documents of data, such as settings, lists and session files: elements with their attributes in order, the elements inside them and their text. The entities XML defines and character references are read, and a document's own entities never are, so a document can't make itself grow without bound. Everything written reads back as it was, line breaks in attributes included.

## Web pages

A page is served from files built into the program with `symbolengine_add_files`, by path from `/index.html`, and every page is also served `symbolengine.js`, its side of the bridge: `symbolengine.call` reaches a native function the program exposed and gives what it returned, or the message of what it threw, or waits for an answer the function gives later, as after a dialog, and the program can run a script in the page and have what it came to, and `symbolengine.on` receives the events the program sends. Values cross as JSON, so a page and the native side read each other's numbers and text exactly. Some systems start loading a page before the web view says it is ready, so the bridge waits for the native side before its first call, and the native side holds what it sends until the page has loaded and its own scripts have run, adding their handlers, though the answers to the page's calls go at once; nothing sent early is lost on any system. A page's name becomes its address, so pages with different names keep what they store apart even in one program; a plugin's editor is named after the plugin's id, so two plugins in one host never read or overwrite each other's stored data. On Windows each program, or each plugin, also gives WebView2 a data folder of its own; CHOC has no setting for one, so the build adds it to CHOC's web view when it fetches it (`cmake/PatchChoc.cmake`), with a second change that passes the keyboard on to the page when its window is given it, as a Mac's web view takes it, and on a Mac a program with its own Edit menu can have Command-C, X, V, Z and A reach the menu instead of the page's text, a third that gives WebView2 a background color to show where the page hasn't drawn, instead of white, and a fourth that binds the program's functions before a page starts loading, on both systems, and stops if CHOC's code has changed under the patch. Linux's web view, WebKitGTK, follows the first release.

A program's own window, `ui::Window`, has the system's title bar, with a maximize button if asked for, and holds one native view, such as a web view, which fills it and is given the keyboard with the window. Its size is in points on a Mac and in pixels at 100% on Windows, which it scales to the screen it is on, so it looks the same size on each; its place on the screens, kept between launches, is held to a screen it can be reached on when it opens. On Windows it takes the program's own icon from its file, as the program's other windows do. It can be maximized, filling the screen beside the Dock and under the menu bar on a Mac, and keeps where it was before that, for the program to keep between launches; on Windows 11 its title bar can take the program's colors, and on a Mac its close button shows a dot while it holds changes not yet saved. Its close button only tells the program, which hides or destroys it, and it can stay see-through while its page draws its first frame, light or dark as the computer or the program says. The system's own dialogs ask questions with buttons of the program's naming, as a sheet on the window they concern on a Mac and a task dialog on Windows, Escape choosing the one named to cancel, and choose a file to open or save, or a folder, by the kinds of file asked for; each is shown once the call has returned and answers when it closes.

On a Mac the program's menus are in the menu bar, `ui::MenuBar`: the app menu, named after the program, holds the program's own items, such as About and Settings, then Services, Hide, Hide Others, Show All and Quit, which asks the program; each menu given after it asks for its items as it opens, and again when the program says what they show has changed, though not while a menu is open, so nothing moves under the pointer. Items have Command shortcuts, with Shift or Option too, can be turned off or ticked, and hold submenus. Windows has no shared menu bar, and a program there draws its menus in its own window, as a page can.

## Applications

Everything in the ui module runs on one thread, the message thread, which runs the message loop, `ui::messageLoop`: the program's windows, web views and menus are made and used there, and any other thread reaches it with `callAsync`, which runs a function there after everything queued before it; `callAfter` runs one once a time has passed, and a `ui::Timer` calls one at an interval for as long as it lives. The loop is the system's own, AppKit's on a Mac and the window messages on Windows, so the system's web view, dialogs and menus run inside it as they do in any program.

A desktop program is an `Application`, in the app module: one per program, made first in `main`, before any window, and run last, its `run()` returning the code the program gave `quit()`. It gives the program its arguments as UTF-8, read on Windows from the command line as the system holds it, so a name outside the system's code page arrives whole. The system's requests reach the program through its callbacks: to quit, from the Dock's menu, logging out or shutting down on a Mac and the session ending on Windows, which the program answers by asking what it needs to and calling `quit()`; to open files, double-clicked or dropped on the program's icon; and a click on its Dock icon while it has no window showing. A program that runs one instance at a time calls `sendToRunningInstance()` when it starts: the first instance becomes the one running, holding a lock the system lets go of however the process ends, and a later instance hands its arguments to it, through the user's distributed notifications on a Mac and a message to a hidden window on Windows, and returns from `main`. Starting the program again with a file's path then opens the file in the window already open; a program run several times at once, as for checks from a script, leaves the call out. The program can also hide itself from the Dock, as a helper nobody should see, add a file to the system's recent documents, say whether it is in front, and end its process at once when its message thread may be held by something it is running. On Windows the program's windows are drawn at each screen's own scaling, and a program started from a console prints to it.

`symbolengine_add_app` in CMake makes an executable target the program as the system sees it: on a Mac an application bundle with its Info.plist written from the name, identifier, version, copyright, the icon's name, the kinds of file it opens and what it says when it asks for the microphone, and on Windows a program with no console and the version information its file's Properties show. The program's own `main` is its entry on both, and it has its name and version as `SYMBOLENGINE_APP_NAME` and `SYMBOLENGINE_APP_VERSION`. [Examples/Hello](../Examples/Hello/Hello.cpp) is a whole program: a window holding a page, the Mac's menu bar, one instance at a time, and the names it is asked to open shown on its page.

## Audio files

The files module reads and writes audio files a stretch at a time, so a file of any length takes little memory, with each channel's samples as floats. A whole number reads as itself divided by 2 to the power of one less than its bits, so a 16-bit sample is divided by 32768, and writes back as the same number; a float is written as the nearest whole number to it times that, held within the format's range, and anything that isn't a number as silence. Float files keep their floats as they are, past full scale too. A file is recognized by what it holds, never its name.

WAV is read whether it says its sizes in RIFF's 32 bits or in RF64's and BW64's ds64 chunk, its sample format plain or in WAVE_FORMAT_EXTENSIBLE, whose speakers it gives. A WAV is written with a JUNK chunk where a ds64 chunk fits, so it becomes RF64 in place when it passes 4 GB; as plain PCM up to two channels, floats with a fact chunk, and WAVE_FORMAT_EXTENSIBLE for more channels or speakers given. AIFF and AIFF-C are read with their samples in either byte order or as floats, and written as AIFF, or AIFF-C for floats. A file's other chunks, such as a broadcast extension, iXML, cue points and LIST, are kept as they are and written back the same, so a recording's details survive an edit; a broadcast extension also reads and writes field by field. A file whose writing was stopped, or that says more than it holds, reads up to its last whole frame, and a chunk of odd length is read whether its pad byte is there or not.

A WAV or AIFF being written can be flushed: its header is rewritten for the samples so far and the system puts it on disk, so a recording stopped by a crash reads to there, and a WAV past 4 GB becomes RF64 then. `BackgroundAudioWriter` writes a file from a thread that mustn't wait, such as an audio device's: that thread copies its samples into a buffer, never locking, waiting or allocating, and the writer's own thread writes them, flushes the file every second or the interval given, and gives each stretch, as the file holds it, to whatever draws or measures the recording. A stretch the buffer has no room for is refused whole, so the recording can say what it lost.

FLAC, Ogg Vorbis and Opus are read and written through Xiph.Org's own libraries, libFLAC, libvorbis with libogg, and opusfile and libopusenc over libopus, compiled from their sources into the files module with their processor-specific code left out, so they build alike everywhere, and every function of theirs hidden inside whatever links them, so two plugins in one host never meet. libvorbis comes from after its last release, 1.3.7, for the fixes made since, one of them to a use-after-free in seeking, and its encoder's leak in setting up 5.1 is mended in a copy of the one file that has it. Their tags are Vorbis comments, read and written as names and values. FLAC is written in 16 or 24 bits, its length and MD5 signature filled in once the samples are all in, with room left to change its tags later; Ogg Vorbis at a quality and Opus at a bit rate. Channels are always in WAV's order, Ogg Vorbis' and Opus' own turned to it as they are read and written. Opus plays at 48 kHz whatever rate it was made from, with the encoder's start-up samples left out, and a stretch read after a jump is decoded from half a second before, as Opus' decoder settles slowly, so it reads exactly as it does when the file is read through.

MP3 is read through minimp3, built in and hidden the same way, exactly to the sample wherever a read starts. A file whose first frame holds LAME's or Xing's information reads without the samples its encoder and decoder put before the audio and the padding after it, as gapless players read it, so the audio lies where it lay before it was encoded; a file without that information reads as it decodes. M4A and other MPEG-4 audio, AAC in ADTS and CAF are read by the system's own decoders, which come with the system and its licenses: AudioToolbox on a Mac, which reads all three, and a WAV or AIFF-C whose samples are coded in a way of their own, such as ADPCM or µ-law, and Media Foundation on Windows, which reads M4A and AAC. Media Foundation reads Windows Media's WMA too, and on a Mac a file of any other kind goes to AudioToolbox, which reads AC-3, AMR, Sun's AU and more, so the files module reads what each system's own players do; `files::readableExtensions()` lists them, for open dialogs. Media Foundation is loaded when a file first needs it, so a Windows without it, as its N editions are, finds those files unsupported and runs everything else, and no thread's COM is started or changed. AAC's priming samples are left out where the file says how many there are, in its edit list or iTunes' iTunSMPB; Media Foundation acts on the edit list alone, so on Windows the files module reads iTunSMPB itself, as Apple's encoder writes it. Channels come in WAV's order. On Windows a stretch read after a jump is decoded from half a second before, so it reads exactly as it does when the file is read through. Linux reads these after the first release.

The reader is checked against files written by other programs, ffmpeg's, Apple's, LAME's and the flac tool's, sample for sample where the format is lossless and by each channel's tone where it isn't, and what it writes is read back by them in the same way.

## Threads and real time

Three kinds of thread, named in every interface: the message thread, which owns windows, web views and plugin editors; the audio thread, which never allocates, locks or waits, and is checked for it in debug builds; and worker threads for everything slow. Every callback says which thread it is on. Nothing is a global singleton the user didn't make; a program creates its message loop, devices and hosts and passes them where they are needed.

## Child processes

Core starts other programs and keeps a link to them, which the host module's scan workers are built on (`ChildProcess`, `ProcessLink`). A child gets exactly the arguments and environment given, as UTF-8, its output goes to a file or nowhere, never a pipe it could wait on, and it inherits nothing else of the program's: no open file or handle, and every signal at its default, though the program may ignore SIGCHLD or SIGPIPE, which a child would otherwise keep. How a child ended is said as its exit code, the signal or the Windows exception, or as unknown where the system took it back itself; killing one confirms it has gone; and no child outlives what started it: destroying its object kills it, and on Windows every child is in a job the system ends with the program, which also keeps a crashing child from waiting on the system's error dialog. The link carries length-prefixed messages both ways over a channel only the two hold, each whole and in order, and says it is lost from a thread of its own the moment the other end goes: its channel closed, a frame that can't be read, the program that started a child ending even when another process holds that program's end open, or nothing heard for a number of heartbeats, counted in beats of its own rather than by the clock, so a computer asleep loses none, and only once the other end has been heard from, so a program slow to start isn't taken for gone. A child that is to end with its program calls `system::endNow`, which ends a process at once, running nothing more of it: on Windows not even its libraries' detach code, which can deadlock once the other threads were stopped holding a lock.

Tests: a helper program started with arguments holding spaces, quotes, backslashes, nothing and text in three scripts, giving each back exactly; its environment with variables set, replaced and taken out; its output added to a file in a folder made for it; its exit codes, a signal or an access violation, and ending at once with no destructor run; a hung child killed and gone by its process ID, and one ended with its object; a program that doesn't exist and a file that isn't one refused with the system's reason; messages from none to 4 MB and from four threads at once crossing whole and in order; a child's end of the link closed, the child ending itself; a child's program killed while a process it started still holds the program's end of the link, the child gone within two seconds; frames longer than any message or of no known kind losing the link at once; a child stopped by the system lost within its silent beats, and one beating never lost; on a Mac and Linux, no file left open in the program reaching the child, and every signal at its default there. All pass under the address and thread sanitizers, and eighteen deliberate breaks of the code are each caught.

## Interfaces

A plugin's editor and an app's screens are web pages in the system's web view, loaded from resources built into the binary; meters and spectrograms drawn this way run at 60 frames a second. The bridge is typed both ways, its native functions and events declared once and checked on both sides. A native drawing surface for interfaces that can't be web pages is a later question, not a starting point.

## Plugins

A plugin is a class derived from `Plugin`, written once, whose static `describe()` gives its id, name, vendor and features. Its constructor adds its parameters, each with an id kept forever, a range, a default, and text for showing and typing its values; decibels, numbers with units, choices, switches and a bypass come ready-made, and so do parameters hosts see and record from 0 to 1 on a linear scale or one even by ratio, as frequency and Q are heard, shown and typed in their own units, which is how plugins already released with such parameters keep the automation their users recorded. Its buses are stereo in and out unless it says otherwise, and it says which layouts it takes: any standard one from mono to Dolby's 9.1.6 and the ITU 9.1.6, each channel named by its speaker, or one of its own. CLAP has no numbers for the wide pair of Dolby's 9.1.4 and 9.1.6, so those two pass only between a plugin and the fork's VST3 and Audio Unit wrappers below, which say so with an extension of the fork's own, and a CLAP host is never given them. A host asks for a layout by its speakers or by its channel count alone, which gives the first standard layout with that many channels the plugin takes, and is told which speaker each channel is for. A plugin is given its channels in the same order in every format, the order of the speakers' numbers, which is VST3's: an Audio Unit host's layout in another order, such as Atmos 7.1.4 with its side pair before its rear pair, is handed over rearranged, which copies nothing. A speaker arrangement a plugin refuses in VST3 stays refused, instead of being asked for again by its channel count, which would leave the host naming the channels for speakers the plugin isn't feeding. The framework keeps each parameter's value where the audio thread reads it without locking, splits each block where the host changes a parameter so that automation is exact to the sample, flushes denormal numbers to zero while the plugin processes, and saves and loads the parameters as JSON unless the plugin saves more. A plugin hears when the host renders offline, so it can take as long as it needs, and tells the host when its state changes outside its parameters, so the host asks to save. An exception thrown in a plugin's code fails the host's call instead of crashing the host.

A plugin's editor is a web page in the host's window, on Mac and Windows, its files built into the plugin. The page is served `plugin.js` beside `symbolengine.js`, which gives it each parameter with its name, range, value and text, and its steps for a choice; it calls a handler whenever the value changes, whether the page, the host's automation or a preset changed it, and sets values in gestures, which the host hears as the begin, value and end events it records automation from: through `process()` while the plugin is processing, and by asking the host to flush them while it isn't. About 30 times a second, or as often as up to 120 when the plugin asks, it may send the page what it measures, such as levels, without the audio thread waiting on anything, and its own functions the page calls can change parameters in gestures as the page does, which the host records the same way. A Mac host sizes an editor in points and a Windows host in pixels, telling the plugin how many pixels a point is.

A resizable editor is held to its limits, and the page can ask the host for a size with `plugin.resize`. It opens at its instance's own size, or the size the user last gave an editor of that plugin, kept in a file once a resizing has rested for 0.6 s, or the size the plugin gives; all fitted to the screen it opens on. The plugin hears of each new size, to keep it in its own state, and can set the size its editor opens at. For checks run from a script, an editor saves a picture of itself when `SYMBOLENGINE_EDITOR_SNAPSHOT` names a PNG, after running `SYMBOLENGINE_EDITOR_SCRIPT` in the page; on a Mac for now. In a debug build, `SYMBOLENGINE_LIVE_FILES=1` reads every page's files from the folders they were built from, so a page is changed and reloaded without building again, and the source folders' paths never reach a release build.

A plugin binary lists its plugins with `SYMBOLENGINE_PLUGINS`, and `symbolengine_add_plugin` in CMake builds it as CLAP, VST3 and Audio Units. Every format is built through CLAP, and clap-wrapper turns the CLAP build into each other format, so a fix lands in every format at once. SymbolEngine builds with its own fork of clap-wrapper, at github.com/cybra/clap-wrapper, whose symbolengine branch adds SymbolEngine's changes to a clap-wrapper release, each a commit of its own: the speaker arrangements above for VST3, channel layouts for Audio Units, where the layouts a plugin takes are offered to the host, Logic's channel orders among them, the wide pair in both, and a value the host sets in an Audio Unit kept in the state it saves straight after, with no render between, as hosts expect of an Audio Unit. The VST3 SDK and Apple's AudioUnitSDK are fetched, pinned by checksum, only when a plugin is built in a format that needs them. Nothing in a plugin is visible outside it but its entry point, so plugins built on different versions of SymbolEngine load side by side in one host.

Every plugin built in the repository is checked in continuous integration: loaded from its binary as a host loads it, made, run and destroyed, on every system and in the sanitizer build, which builds plugins as CLAP alone; by CLAP's validator and Steinberg's VST3 validator on Mac, Windows and Linux; by pluginval, run as a separate tool, at its strictest level; and by Apple's auval on the Mac.

## Moving an existing plugin

A plugin that already ships keeps what hosts and its users have of it. It states its own identity, the VST3 class ID in its description and the Audio Unit type, subtype and manufacturer codes in `symbolengine_add_plugin`, as it was released with them, which clap-wrapper passes to each format, so a DAW session finds it. A test plugin states a class ID, and Steinberg's validator finds it under that ID on every system. It receives the state its earlier versions saved, exactly as the host stored it, so it can open presets and sessions with their settings: a VST3 host's bytes as they are, and an Audio Unit's from under the key its earlier versions kept it under, `AU_STATE_KEY` in `symbolengine_add_plugin`, where it also saves it, so earlier versions open its sessions too. It keeps the parameter numbers hosts recorded automation against.

## Hosting

The host module loads other makers' plugins into a program and plays audio through them: VST3 on the Mac and Windows and Audio Units on the Mac first, with Linux building and testing VST3 hosting without editors, and Audio Units v3, CLAP and Linux editors after the first release. Plugins run in the program's own process, as DAWs run them, and are found by a scan that loads each one in a worker process. A plugin is someone else's code in the program's process, with threads, timers, windows, a locale and floating-point settings of its own, and every way it can misbehave is one the program meets. The module is built against the problems hosts have met, read from other hosts' and frameworks' histories of fixes, the formats' documentation and a scan of a real library of over a thousand plugins, and each is written below as what the module does, with the test that fails when it doesn't. The audio comes first throughout: a plugin that fails, stalls or gives nonsense is never heard, the audio passes it by through its delay, and the program is told which plugin and why.

### The format layer and its tests

Each format sits behind a narrow layer of the module's own (`PluginFormat`), one each for VST3 (`Vst3Format`), Audio Units (`AudioUnitFormat`) and later CLAP, and everything above it is written once: the scan and the list of plugins, each plugin's life and threads, buses, processing, parameters, state, latency, copies for rendering, editors and what happens when a plugin fails. A fake format (`FakePluginFormat`) takes the formats' place for the layer above, its plugins scripted to fail, hang, call back from any thread or change their buses, latency and parameters on cue, with a hook inside every call where a test makes a plugin misbehave, and each checking every call made into it for its thread, its order and what it overlaps. A program gives the host its main thread, a way to run a function there and to ask whether a thread is it (`PluginHost::Options`), as ui's message loop does, so tests turn that thread's run loop by hand, on every system. What a fake can't show is shown by plugins the module's tests build themselves: a VST3 module written straight against Steinberg's SDK, holding one class for each way a plugin misbehaves, chosen by its class name, which is also the test of a module holding many plugins; Audio Units written straight against AudioToolbox; and, for what happens as a plugin's code loads, crashing, hanging, asking a question or built for another architecture, bundles of their own made from one source. Steinberg's host checker, built from the SDK, logs every call out of order, on the wrong thread or with wrong buffers, parameter queues or process context, and its log is a test's pass or fail. Free plugins downloaded for each run, open-source ones first, are scanned, played, saved and restored in continuous integration, as test material only, never shipped. A program's own library of plugins is checked by hand before each release; Symbol Studio's owner has over a thousand.

Tests: Steinberg's host checker's processor, through loading, playing, rate and block-size changes, switching off and on, state saved and restored, a render copy and unloading, logs no error or warning; each lesson's test below runs against the fake, the test plugins or the free plugins, as it names.

### Loading a plugin's code

A plugin's code is loaded on the main thread, its entry function called once, after loading and before its factory, and its exit function once, when the program ends, after every instance and the factory have gone and before its own static objects are taken down, the last module loaded first, however many a program loaded. It is never unloaded before then, whatever its format: code that registered classes, started threads or set timers can't be taken out safely, and some plugins crash when entered a second time in one process. A module that fails to load is let go of and never touched again in that process. Which binary a bundle holds for this system is found by the format's own layout, a VST3's architecture folders on Windows among them, and its architectures are read from its headers before anything loads it: a plugin built only for another architecture is listed as such, never loaded and never called crashed, except an Intel-only Audio Unit on Apple Silicon, which the system runs in a process of its own through Rosetta for as long as macOS has it, under the rules below. On Windows a plugin's DLL is loaded from its absolute path with its own folder searched for the DLLs it depends on, and the process's working directory and DLL folders, which every plugin and thread share, are never changed; a load that fails says the system's reason and the path. On the Mac a plugin whose code no longer matches its signature is stopped by the system the moment a bad page is touched, whatever the program's entitlements, so its first load in any process is in a scan worker, which goes on to play it; the worker also checks, before loading anything, the code the system would run, the program's own architecture or an Intel-only Audio Unit's Intel code, and that of every library it links outside the system, found as the system would find them, and a plugin found that way, or one whose worker the system killed with a code-signing crash report, is listed as changed after it was signed, with what to do: reinstall it. Only code counts, as only code is what the system checks: a bundle's resources and Info.plist can change with the plugin still running, and the half of a universal binary this computer doesn't run can be damaged with no harm done. Code that carries the quarantine attribute and that the system rejects doesn't fail to load: the load waits on a window of the system's, which a worker can't see, so the worker asks the system first and lists such a plugin as not notarized by its maker, unloaded, looking at it again at every scan since the user's allowing it changes nothing else a scan can see. The attribute alone is no reason, as a notarized plugin carrying it loads as usual, and the program never removes the attribute or changes any file of a plugin. Objective-C class names are one namespace for the whole process, so an Audio Unit's editor class is taken only from its own bundle and refused when the runtime gives another plugin's; SymbolEngine names its own runtime classes uniquely, the libraries a program embeds carry names no plugin's share, and a program exports no symbols beyond its entry points. A program that hosts plugins carries what plugins need of their host: on the Mac, library validation off, memory that copy protection and compilers write code into, the privacy descriptions plugins have needed (microphone, camera, Apple Events, Bluetooth, local network, speech) and plain HTTP to the computer itself; on Windows, its message thread initialized for OLE, so plugins can accept dropped files.

### Each plugin's life and threads

Each instance (`Plugin`, made by `PluginHost`) has a state of its own, made, set up, active and processing, and every call into it is checked against that state and against its thread, failing loudly in debug builds and refused in release. Processing runs on one audio thread at a time; everything else, making, setting up, activating, state, parameters' text, the editor and taking down, runs on the main thread, one call at a time. Plugins are made on the main thread one per turn of the run loop, once the program's window is up, so the window draws between them and a slow one is named: "in the background" means later on the main thread, except where a format makes it asynchronous, as an Audio Unit made through `AudioComponentInstantiate` is, its completion handled on the main queue with the run loop turning, since blocking the main thread for it can deadlock against the system's hosting service. While a call into a plugin runs, the plugin may turn the run loop itself, for a dialog or a wait, so the instance is marked busy, and its removal, its project closing, its editor opening and another load of it wait until the call returns. A plugin's notices, a VST3's `restartComponent`, an Audio Unit's property and parameter changes and CLAP's requests, can come from any thread at any moment, from inside the host's own call into it among them; each only records what it says and wakes the main thread, which acts once the current call has returned and the instance is fully set up, so no notice calls into the plugin, takes a lock or waits. An Audio Unit's listeners run on a thread with a run loop of their own, created and disposed there, so they keep coming while the main thread tracks a menu. Taking a plugin out of processing is a request the audio thread answers at its next block, passing the audio by meanwhile; the main thread waits for the answer with a limit and keeps its run loop turning, since a plugin that locks on the audio thread would otherwise deadlock the two, and it never joins a thread that may be inside a call to a plugin. A plugin is taken down in order on the main thread: processing stopped, its editor closed and the run loop turned once, its listeners and the host's timers for it removed, then reset, deactivated and taken apart in the reverse of how it was made, as far as it was made. The last hold on an instance, let go of on any thread, hands its taking down to the main thread and returns at once. No C++ exception crosses into or out of a plugin. Every thread that calls into plugins has a stack of 8 MB, since plugins assume a main thread's. A plugin can change what belongs to the whole process, so after each call into one on the main thread the module compares the floating-point control register, the C locale, the working directory and, on the Mac, mouse-event coalescing with its own, puts them back if they changed and logs the plugin in debug builds, and nothing SymbolEngine writes or reads depends on the locale.

### Scanning

The scan loads each plugin file in a worker process (`PluginScanWorker`), a copy of the program started in a worker mode decided at the top of `main`, before its settings, logging, crash reporting, single-instance handoff or any window, so a worker reads nothing of the program's but its request and writes nothing but its answer. On the Mac it is an accessory from its start, so it never shows in the Dock, and its identity is the program's, so the computer's firewall rules and privacy grants already know it. A plugin that crashes takes down only its worker. The worker loads plugins on its main thread with its run loop turning, as plugins need, while its link to the program and its heartbeat run on threads of their own; each request carries a number and is answered once, as found, found nothing with why, or failed with why, in length-prefixed messages checked before use, and a worker that ends without answering has failed, whatever its exit code. The worker says each step as it begins it, loading the code, making plugin n of m, setting it up, playing it, while the link beats every second from threads of its own, and the time limit counts from its last sign of progress, a step begun or a plugin answered, so a module holding hundreds of slow plugins is never cut off while a hung one is; a worker past its limit is killed, confirmed gone and replaced. A worker ends the moment its link is lost, from its link's own thread, never through its main thread, which a plugin may hold: with `_exit`, or on Windows `TerminateProcess`, since ending normally runs every loaded plugin's detach code, which can deadlock. It also watches the program's process, and on Windows every worker is in a job that ends with the program. Before loading, a worker notes the plugin it is loading; its crash handler adds the signal or exception and a backtrace to that note and ends at once, and the program's own crash reporter never claims it. On the Mac a worker the system killed is matched with the system's crash report, which alone tells a code-signing kill from others; on Windows no error dialog ever holds a worker up. A worker answers, waits for the program to take the answer and ends without unloading anything, so a crash as it ends fails nothing. A worker that can't be started or reached blames no plugin, and three in a row stop the scan with the system's error, naming the worker's file, so security software can be told to allow it. The scan (`PluginScanner`) uses a worker for a set number of files and below a set size, then replaces it, and a plugin that failed in a used worker is tried once more in a fresh one before it is set aside, so one plugin's damage is never blamed on the next; on Windows, where the host catches a plugin's fault inside its call, the plugin is set aside as crashed and its worker let go after the file, as a process that faulted can't be trusted. When a window appears in the worker, such as a license or authorization question, which a thread of the worker's own sees in the system's list of windows on screen, the worker puts its windows above every other program's, the program hands it the keyboard if the program is in front, which since macOS 14 only the program in front can, the limit pauses and the program says the plugin is asking something, with Skip, which ends the worker and leaves the plugin to be scanned next time (`PluginScanner::skip`); scans run one plugin at a time for this reason, with more workers at once only for files whose manifests say all that is needed. A plugin's kind comes from what it declares, an Audio Unit's type, a VST3 class's category or a CLAP plugin's features, read where possible without making it (`PluginFormat::pluginsIn`), and only effects are made, since only they go in a chain: each is made, offered stereo, set up at the device's last rate, activated, given blocks of silence and noise and a short block, read for its buses, latency, parameters and editor, and taken down, so what passes the scan is what the program will play, and a failure records the step it came at. A module holding many plugins is scanned plugin by plugin, each known by its own identity and answered as it finishes, so a crash at one keeps those before it and the scan carries on after it. The folders scanned are the format's own and those the user adds, never a volume or a home folder, each entered once by its real path, links followed and hidden folders passed over, with a bundle taken as a plugin, never as a folder (`PluginScanner::walk`); each format says which files are its plugins and reads a file's stamp and architectures without loading it (`PluginFormat::examine`), and a file built only for another architecture is listed as that without a worker. A file is scanned again when its binary's size or time changes, either way, or its declared version does. A plugin leaves the list only when its folder can be read and it isn't there, a folder that was never made or was deleted being read as empty; one in a folder that can't be read, or on a drive that isn't connected, is kept as not connected. Stopping a scan or quitting fails nothing: what was found of the file in hand is let go and the file left to scan next time, the list is saved every 10 seconds and when the scan ends, and a scan the program quit during carries on at the next start. The order is fixed, by folder and name, with plugins that failed or timed out before and modules holding many plugins last.

Tests: test bundles that crash on loading and on making by a bad pointer, an abort, an exception out of the factory, a stack overflow and, on Windows, a fail-fast, and one that calls `exit(0)`, each set aside with its reason and a good plugin scanned after each unaffected; a worker whose answers come with the wrong number, cut short, empty, twice, after a heartbeat only, or not at all before it ends, none recorded as found; bundles that hang forever on the main thread and on a thread the main thread waits for, timed out within the limit and 2 s with their worker gone by process ID; a module of 500 plugins taking 150 ms each, never timed out, whose 250th crashes, giving 499 found and one set aside; a worker whose link is closed, whose program is killed and whose program quits, gone within 2 s each time; a Windows DLL whose detach code waits on a lock one of its threads holds, its worker gone within a second; a worker that can't be started, with no plugin set aside and the scan stopped after the third; a bundle that shows a modal question on load, its window in front, scanned without being set aside after 120 s; a plugin that frees memory twice, leaves a thread that crashes 2 s later and sets a German locale, followed by three clean ones, none of which is set aside; a module declaring an effect and an instrument whose instrument crashes when made, listed with both kinds and no crash; a folder walk through a symbolic-link loop, two links to one bundle, a bundle inside a bundle and hidden and system folders, finding every plugin once; a binary replaced inside its bundle with the bundle's time kept, scanned again; a scan stopped at a thousand random points, never setting a plugin aside and resuming where it stopped; the program killed mid-scan, its list readable and less than 10 seconds behind; the program's settings folder unchanged by a scan of twenty plugins but for the list; a worker that never shows in the Dock.

### The list of plugins

A plugin is known by its format's full identity: a VST3 class ID's 16 bytes, an Audio Unit's type, subtype and manufacturer codes as raw values, never trimmed, a CLAP plugin's ID. Where it lies is only where it is now. The list keeps one entry per identity with every place it was found, the one loaded chosen by a stated rule, the native architecture first, then the newer version, then the user's folder, and the others shown as alternates; a product's VST3 and Audio Unit are entries of their own, shown together. Each entry holds what the program needs without making the plugin: its name, maker, version, kind, the channel layouts its main buses take, whether it gives audio out, whether it has an editor, its SDK, when it was first seen and when its file last changed, so "updated" means its file changed, not that it was scanned again. A plugin set aside keeps why, with the step and signal or the limit, the file's stamp, the date, and the program's version and architecture, and is tried again by itself when its stamp changes, or after the computer restarts when it was the system that stopped it; the program lists them with their reasons and a Try Again for each. A plugin that holds only kinds the program doesn't use, finds nothing, or gives no audio out once offered stereo is listed as that, never set aside as a crash. The list (`PluginList`) is a JSON file with a format version and one entry to a line, written to a temporary file and renamed with the last good one kept, and read entry by entry, so an unreadable entry is dropped and logged rather than the whole list, and the entries a damaged file lost are taken from the one kept, which a damaged file never replaces; fields it doesn't know are kept in the entries it doesn't change, numbers are written without the locale, and a change of format moves entries over rather than scanning again. It is kept for each architecture the program runs as (`system::architecture`), since a universal program run under Rosetta loads other plugins. Audio Units come from the system's registry, whose cache can lag behind the folders: the program hears the system's notice that the registry changed and offers a scan, a component in the folders that the registry doesn't yet return is listed as installed but not yet seen by macOS, and the program never stops a system process. An Audio Unit v3 standing in for a v2 one with the same codes isn't loaded as it until v3 is hosted. A project whose plugin is missing keeps its card, description and state unchanged and saves them back byte for byte, says what is missing, and can open with any plugin held back. A plugin moved or renamed is found by its identity; when its identity isn't found but its format, maker and name are, the program asks before loading the match with the old state, and a card saved with a newer version than the one installed says so.

### Buses and channels

A plugin's main buses are offered stereo in and out, and its other buses switched off unless the program feeds them, before any bus is read, since plugins answer differently before and after an arrangement is set and some describe their buses only once one is. What the plugin settles on is read back after every change, whatever the call returned, and the program runs it with that. A plugin that refuses stereo is offered mono in and stereo out, then mono in and out, its output then sent to both sides; one that still gives no audio out is set aside with that reason, in the scan as on a card, both negotiating through one function. Buses and arrangements change only while the plugin is inactive, every count is read again after each change, and an array is never passed as null for a direction with no buses. Every process call carries a buffer for every bus the plugin has, an inactive one pointing at shared silence or scratch space, never null behind a channel count; inputs and outputs never share memory, outputs are cleared before every call so a channel the plugin doesn't write is silence, and buffers are aligned to 32 bytes. Event buses are activated before the plugin is and given empty lists, since a chain sends no notes. An Audio Unit is given its full stream format, rate, channel count and non-interleaved 32-bit float, on every bus in use before every initialize, whether or not it already reads the same, and its largest block before initializing too, since above its default of 1,156 frames a unit renders nothing. Each bus's format is read back after initializing, and a mismatch sets the card aside for that layout. Its input callback keeps a position for each bus, gives exactly the frames asked for from there and silence past the block, and never returns success with buffers it didn't fill; a buffer the unit swapped for its own is copied back. A program that wants a plugin run with other than what it settled on, mono rather than fitted to the program's channels, asks for it while the plugin isn't prepared (`Plugin::arrange`), and gets what it settled on: the layout asked for, kept if the plugin later changes its buses, or where the plugin won't take it, the one it would have settled on anyway.

### Processing

A plugin is set up for the largest block any caller passes, a longer block is split, and it is set up again, inactive, whenever the device's rate or largest block changes. A plugin that refuses blocks shorter than its largest, found by the scan, is fed through a buffer of exactly that size, which counts in its latency. Samples are 32-bit unless a plugin says it takes 64. Each process call carries the time. A VST3's process context has the set-up's rate, the position, a count of every sample processed, the device's time and whether the program is playing, each marked valid only when the program knows it, and holds at least what the plugin asked for. An Audio Unit's sample time runs on from 0 by exactly the frames rendered, jumping only with a reset, its host time is in the machine's own ticks, never nanoseconds, and its host callbacks are set before every initialize, answering 120 beats a minute in 4/4 for a program with no tempo, checking every argument for null and allocating nothing. Silence flags are never claimed for an input and never trusted from an output. Every render's result is checked: a block that failed plays as if the plugin were switched off, its input through its delay, never what is in the buffer, and a plugin whose instance is lost is no longer called, and its card says so. A block holding a value that isn't a finite number plays the plugin's dry path instead, the plugin is muted with a short fade and reset before it is tried again, and the program is told which plugin and when. Every thread that processes plugins, the device's and every render thread alike, flushes denormal numbers to zero, puts its floating-point mode back after each plugin's call, and joins the device's workgroup, or on an export thread a work interval of its own; it never reads or calls a plugin's render context observer. Each plugin's time per block is measured around its call against the time the block lasts, its frames at its rate: the share of its blocks' time it took and its worst block since the program last took them, as a meter showing the worst block does (`Plugin::timing`, `takeTiming`), and the blocks it alone was late in, with its longest wait from a discontinuity to its reset where that comes from the main thread, so a main thread kept busy shows (`PluginTiming::longestResetWait`). Whenever a block runs late, whether or not the system says sound was lost, since Windows never tells a program its output came too late, the devices module reports it with what the program says of it, which the host gives: the plugin that alone took longer than the block lasts, or, in softer words, the one that took the most of a late block. Both are timed by the clock, as asking the system for a thread's own time is a system call the audio thread never makes, so a moment the system held the audio up during a plugin's call counts against it, which blames one that only took the most far more easily. A debug mode that traps allocations and locks inside each plugin's process call comes later, as a step of its own. The program's switch for a plugin is its own: switched off, the audio passes through the plugin's delay, so switching never moves the sound in time, the plugin's own bypass is never driven, and its parameter values still reach it; switched back on, it is reset first, so nothing it held from before is heard. A reset, VST3's processing stopped and started, an Audio Unit's `AudioUnitReset`, rendering offline at once on the render thread and in real time from the main thread, which the host wakes at once for it, with its render held off, the unit rendering on until then, or CLAP's reset, also comes at every discontinuity: a jump, a new take and each stretch of a render, never a loop returning to its start, so reverb and delay tails carry over it. While the main thread holds a plugin off the audio for a call that can't overlap its processing, as a reset, a state or setting it up again, its blocks are silent, never heard unprocessed; one not yet set up, or failed, is played past.

### Parameters

A parameter is known by its ID everywhere, in automation, in the program's records and in state the program keeps itself, an Audio Unit's by its ID in its global scope, where effects keep theirs, other scopes waiting until a plugin needs them; indices are for listing only. Values are doubles from 0 to 1, normalized by the plugin's own range, a parameter of n steps mapped as its format says, kept at full precision from the program to the plugin. Flags are honored: read-only parameters aren't written, hidden ones aren't shown, the bypass and program-change parameters aren't automated, and parameters that only stand in for MIDI controllers are left out of the program's lists; IDs a plugin never listed are ignored. The list is read after the plugin's buses are set, since some plugins have none before, and again when the plugin says it changed, rebuilt on the main thread and swapped in for the audio thread without a lock, a parameter that stays keeping its automation and one that goes keeping its recorded data, marked missing. Changes reach a plugin as an ordered list of ID, sample offset and value for each block, gestures included, in queues made for every parameter when the plugin is set up, so a change added on the audio thread never allocates or locks. A VST3's processor hears a change only through a process call, so every change, from the program, a preset or the plugin's own editor, is queued for it and given at its sample, and the controller hears it on the main thread; a value from the controller's own edit is never sent back to it, an edit arriving while the program sets that parameter is taken as an echo, and values the processor reports go to the controller and the program's display. An Audio Unit is given changes while it renders through a queue the render thread empties into it just before each render, never by a call from another thread, since some units lock their render against such calls; each is scheduled at its frame, though a unit built on Apple's SDK hears it from the start of the render, as the SDK sets the value as it is scheduled. A plugin's own edits, and its saying its state changed, on any thread, mark the project changed from the main thread; notices that follow a restore or preset change, for 250 ms or until the values read back match, update the display without marking the project changed or counting as the user's.

### State

A plugin's state is taken and given on the main thread, and taken only once every value the program or the plugin changed has reached the plugin's processing. While the device plays it, the next block carries them and the state is taken after; while it doesn't, a VST3 is given a process call of no samples with its full buffers, never null ones, and a plugin found to ignore that, as some do, is given a short block of silence instead, which is recorded for it; an Audio Unit has every parameter read, and set again in a copy after its state. A VST3 keeps two states, its processor's and its controller's, saved apart, each with whether it succeeded, and given back after it is made and connected, while it is inactive, in order: the processor's, the same bytes from their start to the controller, then the controller's own. Every value is then read back from the controller, except for plugins whose controller doesn't follow their processor, found by the round trip, for which the program keeps each parameter's value itself and gives them after the state. An Audio Unit's state is the dictionary it gives, its document form for projects where it has one and its plain form for presets and copies, kept as a binary property list exactly as given and checked as it is written; it is given after the formats and largest block are set and before initializing, read back, and given again after initializing if it didn't take, and the program then tells the unit's listeners and reads every value itself. The streams a plugin reads and writes accept null out-pointers, report exact counts, never read past their end and start at the state's first byte; a state that fails or comes back empty is recorded as no state and is never given. A plugin's buses, latency and parameters are read again after its state is given, since they can follow it. A program that hosted plugins before can hand over the state its earlier host saved; reading that earlier form is the program's own code.

Tests: a VST3 that ignores zero-sample blocks, one that crashes on null buffers and one that applies changes from a zero-sample block, each set through its controller with no device, switched off and playing, then saved, with the value in the state every time and no crash; plugins with both states, with only a processor state and a controller that doesn't follow it, and with a controller that reads the processor's state from wherever the stream stands, their parameters randomized, saved and restored into a fresh instance, every value and every sample the same; streams handing out a byte at a time, and plugins that seek absolutely; an empty state never given; an Audio Unit whose state lags its last value until a render, copied for an export that uses the new value; Audio Units that fail a restore before initializing, ignore it silently, or take it only after, each opening a saved project with its saved values; one with a value only its document state carries, round-tripping in a project and not in a preset; one returning a dictionary that can't be written, keeping its last good state with an error shown; a VST3 whose latency and channel count follow its state, applied after a restore.

### Latency, tails and delay compensation

A plugin's latency is read after every activation, an Audio Unit's in seconds after every initialize and turned into frames at the rate in use, and again after any change of layout or state, after switching to rendering offline, and when the plugin says it changed. That notice is acted on from the main thread: a VST3 is deactivated and activated again as its format asks, the value read, and the chain's delays rebuilt in one step, new delay lines cleared and the switch crossfaded. The audio thread uses the value the main thread read. A latency over ten seconds is a fault and reported. A chain's latency is the sum of its plugins', switched-off ones included, applied once: the playhead and meters stand back by it while playing, an export reads ahead by it and drops that much, and parameter changes reach a plugin with the audio they belong to. A plugin's tail is read with its latency, and a render through it runs on past the end in silence for its tail, or until its output stays under -120 dBFS for a second, up to a limit for plugins that report an endless tail or none.

Tests: a plugin whose latency is 0 before activation, 256 after, 512 after a parameter change it announces and 1,024 offline, an impulse through the chain lining up to the sample after each, with no stale sample, and a latency of 2^31 - 1 reported as a fault; an Audio Unit reporting 10 ms after initializing and 20 ms after a parameter change, used as 441 and then 882 frames at 44.1 kHz and asked no more than once per change; chains of none, one and three latent plugins, one switched off, an impulse at sample N exported at N and metered at N, and a parameter step written at N reaching the plugin with sample N; a two-second reverb, one reporting an endless tail and one reporting none but ringing, each render ending where the rule says.

### Copies for rendering

An export or render runs through copies of the chain's plugins, never the ones playing: each a new instance made on the main thread, given the playing one's state taken as above, set to render offline before it is set up, since plugins choose their algorithm and latency then, its latency and tail read after, and let go of on the main thread wherever the render finished. The render's thread touches only the copies, never waits on the main thread, and has the stack, floating-point mode and work interval of any thread that calls plugins. A plugin that can't be copied stops the render and says which; one that must keep real time, as its format lets it declare or the user marks it, is rendered at the device's pace. Plugin windows stay as they are, and copies' editors are never shown.

Tests: a plugin that counts its live instances and aborts if two share a call, exported through a hundred times while it plays, the playing one's output never changing; a plugin that adds latency only offline, its export of an impulse lining up to the sample; one that declares it needs real time, its render taking at least its length; an export with a plugin window open that busy-paints, taking no longer than with it closed.

### Editors

A plugin's editor (`PluginEditor`) opens on the main thread in a native view of the program's, as the one a window of its own holds (`PluginWindow`), at most one view per instance, its window resizable only if the plugin's view is. Closing its window always takes the view down, once any call into the plugin has returned, and the plugin is let go of a turn of the run loop later; opening it again makes a new view. A VST3's view is made and its frame set; on Windows its scale is given before its size is first asked for and again once it is attached to the monitor it is really on; it is sized, then attached; and it is taken down by removing it while its parent is still whole, clearing its frame and letting it go before the window goes. Sizes are points on the Mac, where no scale is ever given, and pixels on Windows. A plugin's request to resize, from any thread, is handled on the main thread by resizing and telling the view once, a request repeated from inside that call ending the loop, and a drag asks the plugin for the nearest size it takes; sizes are rounded once, and a size under 100 by 50 points is raised. On the Mac the plugin's view lives in one container view made with its window and kept for its life, not flipped and clipping to its bounds, made a point larger each way and put back once the view is in it, as some views settle their scale only then; the host sizes the first view the plugin puts in it, which a plugin that can't be resized may leave to the host, and never resizes or reorders any other, and its view is never hidden before it is removed. An Audio Unit's view is made only on an initialized unit, from the class its own bundle holds, a class another plugin's took refused, every exception from making it caught, and followed as it sizes itself without the window feeding back, a size of zero taken as not yet known and an origin it moves put back; it is taken out before the unit is uninitialized, as when it is prepared again at another rate, and put back once it is initialized again. On Windows the plugin gets a plain child window made with the editor window's per-monitor awareness, never moved to another parent after it is attached and never painted over by the program, and a change of monitor scale applies when a move ends. Plugin windows are titled windows that can become key; they float above the program's windows while it is in front, and step back while a question, sheet or file dialog of the program's shows or a window the plugin opened itself appears, so nothing waiting for an answer is hidden, all of them kept so by one object of the program's (`PluginWindows`), which looks again as windows show, become key or close and every quarter second, menus and tooltips, which lie above them, never stepped back for. The program's transport keys reach it whatever the plugin's view does with keys, once a press and after the key's event, unless text is being typed, in a system text field or a text input with a place to type at or marked text, as a web-view editor's text field is; keys a plugin's view hands up to its window's view are taken there quietly, the program's for the program. On Windows the program sees every key first and offers any other key to the plugin's view, delivering it natively only when the view doesn't take it, so no key arrives twice. Return goes to a plugin's text field, and closing an editor from a key waits until the key's event is over. A plugin's context menu is a working menu or none, and a plugin's request to open its editor opens it or brings it forward. A plugin without an editor, or whose editor can't be opened, gets the module's own in its window: a web page of its parameters, plain and neutral unless the program gives a page of its own, drawn as its other pages are, each parameter but the hidden ones and the plugin's own bypass shown with a slider, a choice of its steps or a switch and the plugin's own text for its value, a move there reaching the plugin and the program as the plugin's own editor's edit would, in a gesture, read-only ones never set, and values changed elsewhere followed; the window says why the page stands in. The main thread's latency is measured while editors are open, a beat every 20 ms, and a stall past a limit is told to the program with the plugins whose windows were open, those showing first.

### When a plugin fails

A plugin that crashes in the program's own process takes the program with it unless the program can catch it. On Windows every call into a plugin, its process call included, runs inside a structured-exception guard: a fault switches the plugin off, its audio passing by through its delay, names the plugin and the call, and tells the program the process can no longer be trusted, so it saves the project to a new file and asks to restart; the plugin is never called again in that process. On the Mac nothing carries on after a signal. Around making a plugin and every call into one, on the main thread and the audio thread alike, the host records which plugin and which call in the program's crash note (`PluginCrashNote`), a small file kept in memory the system writes itself, a few stores costing a few tens of billionths of a second, so a run that ends in the middle of one, however it ends, the system stopping it outright among the ways, leaves the note saying so; where the program turns it on, a crash handler adds the crash, a backtrace and the thread it came on, using only what is safe in a crash, then lets the crash go on as it would have, to the system's own report. At the next start the program reads how the last run ended, and a project whose last opening ended inside a plugin can offer to open with it held back. The messages between a VST3 plugin's two parts, which the host hands over on the main thread, are made as the host's own calls are, guarded the same way and never handed to a plugin that has failed, and a plugin that crashes on Windows has its editor's view hidden at once, so the system sends its code nothing more through it. An Audio Unit running out of process can be lost while the program runs on: the program marks it lost, closes its view, says so and offers to make it again from the last state taken. A plugin that blocks in its process call can't be stopped, only measured and named.

Tests: test plugins that throw an exception from their state call and, on Windows, write through a null pointer in their process call and in their view, the program staying up, the chain playing past them and the event naming the plugin and the call; a program killed in the middle of a call into a test plugin on the main thread and on the audio thread, and one crashing inside such a call, its next start reading which plugin and call it ended in, with the crash and a backtrace in the plugin's code, a clean end and a crash outside every call blaming none and a note cut short reading as nothing; an Audio Unit whose instance is lost while playing, the program playing on.

### Finding what a plugin shouldn't call

A plugin that allocates, takes a lock, sleeps or reaches for a file on the audio thread plays perfectly until the moment it doesn't. Nothing in a test's output shows it, and a late block says only which plugin was slow, not why. So a host can be asked to watch for such calls, `PluginHost::Options::watchUnsafeCalls`, a debug mode with the audio playing on: nothing is stopped, and each plugin keeps a list of what it was found calling (`Plugin::unsafeCalls`), the program told once for each new place (`PluginChange::unsafeCall`).

Each entry says what was called and its kind, memory, a lock or a wait, a sleep, a file, a thread or the network; which call into the plugin it came during; how many times, in how many blocks, and the first and last of them; and the way there, stopping where the plugin's own code does. The first and last block are what tell set-up from trouble: a plugin often allocates once in its first block, and the system binds what a plugin calls for the first time, a lock's first use making several calls where later ones make one, so a program looks past those rather than a switch hiding them. Whether the plugin's own code is on the way is said too. A system library's call counts as the plugin's when the plugin called it, and a call with none of its code on the way, as Apple's own code on the way into an Audio Unit might make, is told apart as the system's or the program's. So the host's own path through a block is checked by the same means: a test plugin that calls nothing has nothing found through hundreds of blocks.

Up to 64 places are kept for each plugin, with those past them counted, a place being the call and the innermost twelve frames on the way to it. A record is written only by the thread playing the plugin, with no waiting and nothing allocated, the stack looked at without either, and read from any other. Only a plugin's own calls on the audio thread are watched: what a thread of its own does, or what the program does between its calls, isn't held against it, and only trying a lock, or giving back no memory, isn't found at all, as neither can wait. An offline render isn't watched at all, as nothing is waiting for it: a plugin may rightly wait there for a thread of its own to catch up, as one that took up changes in time for the block they belong to does.

How the calls are seen is each system's own, none of it needing anything of the plugin, however it was built:

- **Mac and Linux.** A program links `SymbolEngine::host_unsafe_calls`, a small library of its own that stands in for each such function, or the system inserts it into a program that wasn't, with `DYLD_INSERT_LIBRARIES` or `LD_PRELOAD`. Standing in for them in the whole process is what lets it see inside the system's libraries, as a string growing in the C++ library's own code or CoreFoundation allocating through its zones. It has to be there as the program starts: on a Mac, measured, the same library loaded before the plugin, or the same table in the program itself, sees nothing at all. It costs about 5 billionths of a second a call on any thread, watched or not, so it belongs in a debug build. A thread's own storage can't say whether it is being watched, as first touching it may allocate from inside the allocator, so a key of the thread's does.
- **Windows.** Every module calls another's functions through its own table of imports, so the host points each table's entries for such functions here, in every module in the process, as it is asked to watch and again as each plugin is prepared. Nothing is linked. What a module looks up by name as it runs goes straight to the function and isn't seen, nor is a library loaded since the host last looked. A Debug build's runtime takes a lock of its own for every checked iterator made and around its heap, which a report shows as `EnterCriticalSection`, the host's own told apart from the plugin's, and a release build doesn't.

`PluginHost::canWatchUnsafeCalls` tries it for real the first time it is asked, a memory call and a lock under its own eye, so a library loaded too late, or something else in the process taking the same calls first as the address sanitizer does, says false rather than finding nothing. A host asked to watch where it can't simply doesn't.

clang's real-time checker catches much of this on a Mac and Linux, and is the better tool for a plugin's own developer, building their own code with it. It isn't what the host uses: it doesn't run on Windows, the compiler a Mac comes with doesn't carry it, it prints and stops rather than telling a program which plugin it was, and its list has none of the functions a Mac's own libraries allocate with.

What it can't see: a plugin running in a process of its own, as an Intel-only Audio Unit does through Rosetta on Apple Silicon; a plugin with an allocator of its own that gets its memory ahead of time, which is no fault; and a system call made without going through any library.

Tests: a test plugin built on its own, knowing nothing of this, told by a parameter to allocate through the C library, `new`, a vector, a string growing in the C++ library's own code and what the system's own libraries allocate with; to take a mutex, a system lock and a read-write lock, wait on a condition, sleep, open a file and start a thread; each found as what it is and traced into the plugin. Only trying a lock and giving back nothing, found as nothing. Three plugins played in turn with one misbehaving, only it named. A worker thread of the plugin's allocating during its call, the plugin's main-thread calls, the program's own work between calls on the same thread, and an offline render, none found. Allocating only in one block, in every tenth, twice in each, and as processing starts, each counted as it is. A hundred places, 64 kept and the rest counted, the audio playing on. The list read throughout play. A fake plugin allocating in the test's own code, said not to be plugin code. An Audio Unit that allocates in its render found, and one that doesn't having nothing past its first blocks. And in a program not linked to the library, with it loaded after the program started: can't watch, and a host asked to is unharmed.

### Audio Units v3 and CLAP, after the first release

Audio Units v3 are made asynchronously, in process only where their maker packaged them for it, with their rate set through each bus's format and their largest block set before their render resources; their parameters are known by key path, an address being only a cache, and their tree can be rebuilt under the program; their view controller arrives later and may report no size; projects keep their state for documents and presets their plain state; an extension that crashes invalidates its instance, which the program survives and says so; and v3 extensions are registered from wherever their app lies. A CLAP plugin has no audio ports without the extension that describes them, and its ports change only while it is inactive; the program keeps CLAP's thread contract and answers its thread checks truthfully; a scan reads a module's descriptors without making instances, and its preset discovery runs in the worker too; a plugin's life is followed exactly, and deactivating never waits forever on an audio thread that stopped; its requests to restart, process and call back set flags the main thread and audio thread act on within a frame; parameter changes go through processing or a flush, never both at once; its state streams may move a few bytes at a time; its latency changes only while it is being activated; and its editor is embedded where it can be, floating otherwise, sized in its own API's units. Each comes with its test as those formats are built.

## Devices

The devices module plays and records through the system's audio devices: Core Audio on a Mac, and Windows Audio in shared and exclusive mode and ASIO, with the developer's own SDK, on Windows. It is built against the problems audio software has met with devices, read from other frameworks' and products' histories of fixes, the system makers' documentation and long takes recorded on real devices, and each is written below as what the module does, with the test that fails when it doesn't. A recording comes first throughout: every sample an input captures reaches the program once, in order and at its place in time, or the program is told where and how much is missing.

### The system layer and its fake

Each system's calls sit behind a narrow layer of the module's own, one each for Core Audio, Windows Audio and ASIO, and everything above it is written once: the device lists, choosing and restoring devices, the control of each device, the audio callback's contract, the timeline, two devices on two clocks and the events the program hears. In the tests a scripted fake takes the system's place. Its devices call back from threads of their own with the block sizes, positions, timestamps and flags the test gives; it sends the system's notifications from any thread, several at once as the systems batch them; it delays, fails or blocks any call and applies a change late; and it replays sequences recorded from real hardware by a small recorder, such as a Bluetooth headset switching profiles, its clock keeping the session's time while no device moves it on. Sessions recorded with the owner are kept as tests, trimmed, each quiet stretch shortened and every device's identifier and name replaced: a Mac and a Windows PC each slept, its USB interface unplugged and plugged back in and a Bluetooth headset connected, a stream on the interface stopping for each sleep, opening again once awake and lost with the interface, and an output following the default moving with it as the headset came and went, across both sleeps and the hub unplugged, and never lost. Frames, samples, bytes and time are types of their own, so a size counted in one is never read as another, and the systems' structures come from their own headers, checked by size and layout where the module must declare them itself. So nearly every lesson below is a test that runs in continuous integration with no audio hardware. What a fake can't show, two real clocks drifting, a Bluetooth headset, sleep and a driver's own quirks, is checked on real devices by hand before each release.

### Threads

Each open device has one control thread that owns its state, and every change goes through it in turn: opening, starting, stopping, closing, a new rate or block size, and rebuilding after the system changed the device. The system's notifications and the audio thread only tell it. A notification copies what it says and wakes the control thread; it never calls back into the system, blocks, adds or removes a listener, or lets go of the last hold on a device, since a system can hold its own locks while it delivers one and a call back in deadlocks against a stop under way. Every request ends on every path, failures included, with its new state set before whoever waits is woken. Starting and stopping never hold a lock the audio callback takes, since a system can run the callback inside the call that starts it. Stopping and closing always return within a bound: every wait on a device has a time limit, and a system thread that never comes back leaves the device failed, its memory kept instead of freed under that thread. A program that stops a device from inside its own audio callback or a notification gets an error at once, never a deadlock, and the callback asks to stop through what it returns. The program hears what happens through typed events, delivered in order on the thread it chooses, its message thread in a program with one, or a thread of the stream's own: the device list changed, a default changed, a device was lost and why, a format changed, a dropout, a stall, started, stopped and errors. An error keeps the system's own code and the step that failed, a warning never fails what it came from, and an error repeated is counted instead of logged each time.

The audio thread never allocates, frees, locks, waits, makes a system call or logs; a program's tests count every allocation made on it by including `AudioThreadChecks.h`, and the module's own tests require none. Every buffer it touches is made when the device opens, for the largest block the device can give, and touched once before it starts, so it never faults on a page while it runs. It flushes denormal numbers to zero and leaves the rounding mode alone. Its priority is read back after it starts and reported, since a system can refuse it quietly: on Windows the thread is registered with the multimedia scheduler as Pro Audio when the device starts and released when it stops, on the same thread, and on a Mac threads that work to the device's deadline join its audio workgroup and leave it before they end. Threads writing to disk are raised, never real time.

Data crosses between threads through core's lock-free buffers, which pass it from one writer to one reader in acquire and release order, hold exactly the capacity they say, and check in debug builds that no two threads write at once or read at once. Waits and timers run on the steady clock, so a clock set back delays nothing, and allow for waking early. Reading ahead for playback and writing a take run on threads of their own, so a stalled read never holds up a recording.

Tests: a fake device whose call never returns, and one that never confirms a stop and then calls back once more, both stop within the bound with nothing freed under the late call; notifications sent from random threads, the audio thread among them, reach the program one at a time, in order, on the message thread; a fake that runs the callback inside its start while holding a lock its property calls take never deadlocks; a stop from inside the callback returns an error; eight threads starting, stopping, changing the rate, adding and removing callbacks at random, against injected losses, for over a thousand calls, end with every call returned in its time; the audio thread runs an hour of blocks, with dropouts and blocks split on the way, allocating nothing; a denormal number made on it comes out as zero; two threads pass chunks of random sizes through a lock-free buffer with every item arriving once, in order.

### The callback

Each callback hears that the device is about to start, with its settings as they finally are, before its first block, and that it stopped, exactly once, after its last. A device the system restarts stops and starts again in that order; a callback added while the device runs hears it start before its first block, and one removed has had its last block when the removal returns. A block holds any number of frames from one to the largest the start announced, since systems hand out blocks of other sizes than they said: larger ones are split, and a block of none is never delivered. Outputs arrive silent and a channel the program didn't open stays silent, so an input never sounds through the speakers unasked. Each block's input is the input of that same cycle, never the cycle before, which would put every recording a block late. Each block carries the 64-bit positions of its first input and first output frames, which count every frame lost as well as every frame delivered, and the host times when its input was captured and when its output will be heard, on one steady clock. On a Mac that is Core Audio's host time converted by the machine's timebase, which on Apple Silicon isn't nanoseconds, the input's taken from the input timestamp and the output's from the output's, each used only while Core Audio marks it valid. The load each block puts on the audio thread is measured against that block's own length, and blocks that overrun their time are counted.

Tests: a fake device that restarts itself at a new rate and size while callbacks are added and removed from another thread gives each callback the order above; blocks of random sizes from none to three times the announced one, primes among them, reach the program within the announced size with every frame kept; an eight-channel fake with noise on every input and a program writing nothing gives exact zeros on every output; a fake that stamps each cycle's number into its input finds the program's callback given that same cycle's number; positions carry on past 2^31 and 2^32 frames; two callbacks' outputs are added together.

### The timeline

A recording keeps real time. Every frame an input captures is delivered once, in order, or counted lost at its place. A gap the system shows becomes a dropout of exactly the missing length at its position, and the positions of the blocks after it count it, so the program can fill it with silence or note it: Windows Audio's discontinuity flag or a jump in its device position, a jump in Core Audio's sample time or an overload, a jump in ASIO's sample position or the driver asking to resync. Nothing is padded, repeated or dropped to catch up. A packet the system marks silent is zeros, whatever its buffer holds. A start begins clean: the first frame delivered was captured after the start, every buffer and converter is cleared, and a start that drops warm-up frames says how many. A watchdog off the audio thread compares what each direction delivers with the steady clock. No frames for three of its blocks while the device still says it runs is a stall; the first block never coming stops the stream and says why, such as no clock; and far too many frames for the time is a device running away. A block the callbacks take longer over than it lasts is late, said whether or not the system says sound was lost, with what the program says made it late, asked of the program on the control thread with the time the block spanned (`AudioStream::Options::describeLate`), as a host names the plugin that took that time; the first after a second of none is said at once, and those within a second of the last said together, as one counting them, the worst of them described. The watchdog rests while the device is stopped and across the computer's sleep. An input that gives nothing but exact zeros for a while is said, as a microphone that the system or its privacy settings deny, a muted input and a dead cable all give zeros and no error. A device whose rate, format, channels or block size changes under it, by another program, the hardware's own clock or a Bluetooth headset switching profiles, ends that stretch at its last good sample, opens again as it now is, and says what changed from and to. Samples at a new rate never join a stretch at the old one.

Tests: a fake device that stops calling back while it says it runs is found stalled within three periods, the recording holding exactly the frames it gave; one that calls back as fast as it can is found running away; a callback taking 15 ms over a block of 10.7 ms is said late at once, with the time it spanned asked about, and five more within the second said together, counted, the worst of them described; one whose first block never comes fails its start; packets at positions 0, 480, 960 and 1920 with the discontinuity flag on the second and fourth give exactly one gap, of 480 frames at 1440; a gap flagged with no positions is a dropout of unknown length, except on the first cycle; a silent packet of random bytes reads as zeros; a counting sequence through cycles of every size and gaps of every length reaches the program at its own positions; thirty seconds of exact zeros on an input is said and noise at -120 dBFS isn't; a rate change from 48 to 44.1 kHz during a take, its notifications sent twenty times from four threads, opens the device again once, puts no later sample in the 48 kHz stretch and leaves the device at the rate the other program set; a notice that changed nothing opens nothing again.

### Two devices, two clocks

An input and an output on different devices run on two clocks, unless the system says they share one, as Core Audio does with each device's clock domain, and at a hundred parts per million they part by 360 ms an hour. They are never joined by a buffer of fixed size, which in time must run over or dry up, nor run together at the output's pace, which fills an input block that came late with silence: an overnight take recorded that way held 29 gaps of exactly one block. The input sets the time. A recording is written from the input's own thread, paced by nothing else and never resampled, so its samples are the interface's own. What crosses to the other clock, the input heard through the output and playback heard against a recording, goes through an adaptive resampler on the playback side (`AudioBridge`), driven by how full its buffer is against its target, read at each output block's time from the input's count and the host clock both streams' blocks carry, so the ratio of the two clocks shows as it builds and not only when a whole block more has come; the loop's integral settles at the drift, which it reports. A Mac can join two devices into one aggregate that corrects their drift, but it does so by resampling every device in it except the one chosen as its clock, so the module keeps the devices apart on a Mac too and corrects the drift itself, the same way on both systems.

Tests: a fake input running 100 parts per million fast and a fake output at 48 kHz, on threads of their own, through eight hours of fake time with every sample numbered, record every number once, and the monitor's delay stays within its bound; the same one percent apart, and with the output stalled for two seconds; on real devices, a USB interface in and the computer's speakers out overnight, the take's length against the interface's own sample clock and the drift reported.

### Device lists and identity

A device is known by the system's own lasting identifier, Core Audio's UID, Windows Audio's endpoint ID or an ASIO driver's class ID, kept with its name, its kind and its place among devices of the same name, since names repeat, as two of one interface do, and change, and a list's order and the system's object numbers change when a device comes back. A saved device is found again by its identifier first, then by a name only it has, and the program is asked when that leaves more than one. Lists, and what each device offers, come from the system's properties without opening a device or setting anything: making a device only to ask about it has changed the system's device list and crashed the program reading it, opening a stream to test a format has stopped another stream already running on that device, and loading every ASIO driver to list them has hung programs as they started and cut other programs' sound. What a device offers is kept, and read again when the list changes. A process opens one stream per device, which is shared or refused. A device that fails to answer is listed as failed and the rest are listed; one whose calls never return is marked as not answering after a time limit, off the message thread; and no devices at all, or no default, are ordinary states. A system layer that fails to start is an error, never a device that plays and records nothing.

Tests: devices that share a name are numbered among themselves, and a device whose identifier changed is found by a name only it has, or asked about when two have it; listing devices and listing them again make no call that opens or sets anything; the second of four devices failing to answer leaves the other three listed; a device whose call never returns is marked as not answering and listing finishes; a second stream on one device is refused, and allowed once the first has closed; a device added and removed a hundred times while another records changes nothing in the recording.

### Choosing and restoring

Each direction is saved apart: a device chosen, the system's default followed, or none, and none stays none when it is restored. The kind of driver, Windows Audio or ASIO, is saved with it. Channels are the device's own, chosen one by one and never mixed up or down unasked, and saved channels a device no longer has are said, never recorded as fewer without a word. Restoring falls back direction by direction and setting by setting, so an input that has gone leaves the output, its rate and its block size alone. It tries the system's default first, and leaves out a headset's hands-free microphone and loopback devices unless the user chose one before, since opening a Bluetooth headset's microphone drops its playback to voice quality; every device put in another's place is said; and resolving again when the list changes finds the device chosen when it returns, for the program to take it back while nothing records. Restoring never opens an input the program didn't ask for, so the computer shows its microphone in use only when it is, and a program playing through a device that also records leaves the device's input off. The device's current rate is a choice of its own. A saved rate or block size the device still offers is restored exactly, and otherwise the nearest it offers is used, by a stated rule, and said; block sizes are read again after the rate changes, since they depend on it; what the device runs at is read back once it opens; and what is saved is what the user chose, never what the device happened to give. A setting is changed only on the user's word and only when it differs, since some drivers fail when set to what they already are; a rate another program changed is never set back, which leaves two programs fighting; and a device another program is using is said to be shared before its rate changes. A new choice that fails to open leaves the one before it running.

Tests: an input saved as none stays closed when restored, with a fallback and without one; the saved input gone leaves the output exactly as saved; a fake hands-free headset is never chosen as a fallback; a device that returns is resolved as chosen again; a rate or block size the device doesn't offer is put in place by the stated rule and said; a device whose rate reads 0 is given one it offers, and one that fails when set to its own rate is never set to it; saved channels the device no longer has are said; a change that fails to open leaves the stream running as it was; a setup reads back as it was saved, and one garbled reads as the defaults.

### Losing a device

A device lost while it runs ends its stretch at the last sample it gave, and the loss is said with the device and the reason: unplugged, taken by another program for its exclusive use, stopped answering, or gone when the system's audio service restarted. Nothing takes its place during a take. The module never moves a recording to another device; a stream that follows the system's default output moves when the default changes, as when headphones are plugged in, but an input never moves while it records. Whether a take carries on when the same device comes back, with the time it was gone marked, or ends there, is the program's choice, and the device comes back by its identifier, since the system gives it a new number. A change to another device never touches an open one. The system's word that a default changed is a hint, sent for each role and direction and sometimes twice for one change, so the module asks again for its own stream's default and acts only when that differs.

Tests: a fake with two inputs, recording from the first, which is then removed: the recording holds exactly the first input's frames, the event names it, and the second is never opened; a device that goes quiet with no word and then leaves the list is lost; removing an unrelated device restarts nothing; an input-only device removed is said for the input alone, an output on another device running on; a device taken by another program is lost with that reason and the system's code; a burst of default-changed notifications from several threads makes one change, and a notice with nothing changed makes none; the system's audio service restarting loses the stream, and starting it again opens it from new system objects.

### Sleep and power

A take holds the computer awake, which stops idle sleep but not a lid closed or Sleep chosen, as the program is told so it can say; the computer going to sleep ends the stretch, and on waking the devices are checked again and started after a short wait, from new system objects, since a stream started as the computer wakes can fail. A program recording with its window hidden is kept out of the system's power saving for programs in the background, App Nap on a Mac and the slower speed Windows 11 gives a program it judges to be in the background, and the thread writing to disk is woken by the audio thread's signal, never by a timer.

Tests: a fake sleep and wake ends the stretch as the computer sleeps, starts nothing while it sleeps or in the wait after it, and says how long it slept when it wakes; on real devices, sleep with a wake timer during a take on a Mac and on Windows, and an overnight take with the window hidden.

### Latency

Latency is reported for each direction in frames, every buffer counted, and as unknown when the system gives nothing, never as 0: on a Mac the device's latency, its safety offset, its block and its stream's latency, read again after every change; on Windows the stream's latency with the buffers; for ASIO the driver's, read once its buffers are made and again when it says they changed. Systems misreport it, so a loopback measurement, out through a cable and back in, is kept for each device, rate and block size, recordings are placed by it, and each take keeps the correction it was placed with.

Tests: a fake duplex device with a known delay inside it measures through the loopback exactly that delay with its buffers, and a module that adds a cycle fails; a fake giving each part of the latency a different prime number reports their sum; a latency of 0 reads as unknown.

### Core Audio

Listeners are blocks on a private queue, so notifications arrive in a program whose main thread is busy or that has none, and each handles every property in a call, since Core Audio sends several at once; the context a listener reaches lives until after it is removed, with exactly the address, scope and context it was added with. Every property read can fail and is checked for the size it returns, and a property that isn't there falls back, as a channel with no name takes its number. Setting a rate or a block size takes effect later, if at all, so the module sets it, waits for Core Audio's word with a time limit, reads it back and reports what it is. A device's block size is shared by everything in the process using it, input and output alike, and the smallest asked for wins. A device is a list of streams, each with its own channels, interleaved or not, and some switched off with no data: its channels come from its stream configuration, never from its channel layout, and each cycle's length from each buffer's own size. The module listens on each device it uses for its rate, its formats, its streams and their configuration, a change of its own, its clock source and whether it is alive, and on the system for the device list, the default devices and the audio service restarting, which leaves every object number stale. The rate a device actually runs at is compared with the one it was set to, which shows an external clock that has lost its lock. Before opening an input the module asks whether the program may use the microphone, and a denial is an error of its own, since Core Audio delivers silence to a program it denies; the process's input mute is shown. A program playing through a device that has inputs switches their streams off before it starts, so the microphone indicator stays off. Input past full scale, as a built-in microphone gives at high gain, is kept as it is, and conversions to whole numbers hold to the format's range. An output with nothing to play stops after a moment, so a headset can move to another of the user's devices. The module never takes a device for its own exclusive use, and a device another program has taken is an error naming it. A Multi-Output device feeds each of its devices the same output, and an aggregate the user made is taken as it is, its channels counted from its streams in the order of its devices, and rebuilt when a device in it changes. A stop gates the callback by a flag the callback reads, keeps the callback's context until Core Audio has let go of the callback, and never waits for the device to say it stopped, which it doesn't while anything else in the process still uses it.

Tests: host times given in ticks at a timebase of 125/3 come out in nanoseconds; listener calls of twenty addresses at once, some after removal, from random threads, while a device opens and closes ten thousand times under the address and thread sanitizers; a rate that applies after 300 ms, one that never applies, one that applies another rate and one that reverts; layouts of one stereo stream, two mono streams, five six-channel streams, mixed interleaving and a stream switched off, each channel's samples carrying its number; a recorded sequence of a Bluetooth headset switching profiles; a device that stops being alive, one that goes quiet with no word, and one whose reads start failing as a removed object; on real devices, a USB interface unplugged during a take, and the audio service restarted during one.

### Windows Audio

Streams are driven by the system's events, never polled, since timers on Windows 11 can be coarse for a program whose window is minimized. In shared mode an input's buffer is sized for the longest its thread may be held up, hundreds of milliseconds, apart from the block it delivers each period, and the size the system gave is read back: an input given one period of buffer lost audio about four times an hour in a 13-hour take, each time its thread came late, and with 200 ms it lost nothing. Each wake reads every packet waiting, until the next packet's size is zero, so a backlog after a late turn is passed on at once. Every packet's flags are read: a discontinuity becomes the gap its device position shows, the flag on the first packet after a start counting only when the position jumps; a silent packet is zeros; a time marked in error is left out; and each packet's device position and performance-counter time place it. Each buffer taken is given back once, whole or not at all, on the thread that took it and within its period, and never after a failed take; an empty buffer is no error. In exclusive mode the module tries the formats a device may take, floats, 32 bits, 24 bits in 32, packed 24 bits and 16, and the system's own setup has the last word; a size the system calls unaligned is set up again on a new client at the aligned size; one whole buffer is taken for each event; the input and output may have different sizes; and exclusive mode refused is an error, never shared mode in its place. Shared mode runs at the system's mix rate, so a recording opens at the device's own rate or says what converts it, and a device set to fewer bits than the take records is said. A recording asks for the device's raw stream where it offers one, since the system's and the maker's audio effects otherwise reach the recording, never uses the communications category, and opts out of being turned down when another program starts a call; each take records which stream it got. Shared mode's low-latency periods are left off for recording. A session the system ends says why: the device removed, its format changed in Sound settings, another program taking it for its exclusive use, the audio service stopped or the user logged off; a toggle of the device's enhancements, which only changes a property, is checked and rebuilt when it changed something. A device notification only copies what it says and wakes the control thread, and the object that receives them outlives any call under way. An input that the privacy settings or security software refuse is an error saying where to allow it, never a silent device in its place. A format structure is read only as far as the system says it reaches, and a channel mask of zero means channels in order. Threads the module makes start their own COM and never change a caller's. Each failed setup is tried again on a new client, the event handle is always set, and every object is given back in the order it was taken, so a thousand opens and closes leave nothing behind. A Bluetooth headset's hands-free endpoints are known as such, by the bus that enumerated them, since Windows 11 names AirPods' microphone with no word of its profile, and its stereo output is never paired with its hands-free input. A program's streams show in the system's volume mixer as one, under its own name.

Tests: a 200 ms buffer with its thread held for 50 ms every two seconds through an hour of fake time loses nothing, and a one-period buffer fails; a 400 ms hold loses exactly the excess, said where it fell; one event with N packets waiting delivers all N; a strict fake that enforces taking and giving back buffers, with failures between the two; the unaligned answer with a size of 1056 frames sets a new client up at that size; a nearest format at another rate isn't taken as supported; a fake whose raw stream must be asked for before every setup, rebuilds included; access refused at activation and at setup each give the privacy error; real COM on a hosted runner, where calls from single-threaded, multithreaded and COM-less threads all work and leave each caller's apartment as it was; on real devices, a take with the window minimized on Windows 11, a monitor carrying the sound left to sleep, and another program opening the device for its exclusive use during a take.

### ASIO

ASIO drivers are listed from the system's registry without loading any, each by its name alone and marked unread, and one is loaded when a stream opens it, since most can't be loaded twice, a process holds one at a time, and loading them to list them has hung programs and cut others' sound; what it has is listed from then on, and the lists change. A setup chosen on a driver not yet read is taken at its word, its channels, rate and block size as saved, and a driver is never loaded in another's place. Drivers built for another processor, or whose file is gone, are listed as such, and two known to misbehave, wrappers of the system's older drivers, are left out. An ASIO input and output are always the same driver's, and a device open through ASIO and Windows Audio at once is said. Every call to a driver is made from one thread the module owns, a single-threaded COM apartment with a message loop, which gives the driver a window of its own, and follows ASIO's states in order, loaded, initialized, prepared with its buffers and running, never making buffers twice or letting go of a driver still prepared. A fault in any call to a driver is caught, the driver is let go and the program told; letting go is always tried, and a driver that faults then is left loaded instead of crashing the program. Structures handed to a driver are larger than it needs and cleared, since drivers write past them, and its strings are bounded and read as UTF-8 or the system's code page. All four of a driver's callbacks are given, since drivers call whichever they choose; before the start and after the stop they write silence and say the output is ready, and nothing in them blocks or calls the driver. At each buffer switch the module reads that half's input, calls the program, writes that half's output and tells the driver it is ready, every cycle; both halves are cleared before the start and the stop, and a half the program didn't write goes out silent. The module says it supports time information, and each cycle's sample position against the one expected finds a dropout; a driver saying it overloaded is a dropout only where it gives no position, as the flag Windows Audio sets is, and one asking to resync is opened again. A driver asking to reset, to change its block size, to resync or to say its latency changed only asks its stream to open it again, which a stream being opened again takes as answered by that opening, so a driver resetting at every open is opened again once; the request wakes the control thread, which waits while the driver's control panel is open, then stops, lets go of the buffers and the driver, loads it again, reads its channels, sizes, rate, latencies and names afresh, starts, says so and marks the gap; making the buffers, if it fails after that, is tried once more at the driver's preferred size. The rate the driver runs at is read after it opens, after every change asked of it, on each of its messages and from its time information: a notice of the rate it already has is passed over, a rate of 0 is a lost clock, and a recording whose rate changed ends that stretch. A driver opens at the rate it already runs at unless the user changes it. Channel counts are read again after any change of rate, a reset or a failure to make the buffers, since a device's channels can depend on its rate, and counts that can't be right are taken as the device lost. Each of ASIO's sample types converts exactly, every container width, count of valid bits and byte order, each channel by its own type. A driver's block sizes are offered as it gives them, its preferred one first, and opening it again never changes the size it keeps. Initializing has succeeded only when the driver answers more than 0. The control panel opens from the driver's thread and may return at once or only when it closes, and everything is read again after it. The ASIO SDK is the developer's, under Steinberg's terms, and never in the repository.

Tests, against fake drivers the tests make in place of the registry's: listing loads no driver and choosing loads one; a driver that fails any call from another thread or out of its order of states is taken through every path; one that faults in each call in turn; one that writes a kilobyte past each structure and gives unterminated names, with guard pages; one that calls back while its buffers are made, after the stop and after its buffers are let go; one that stamps its switch count into the input, which the program must see in the same cycle; jumps in the sample position and requests to resync; resets while opening, while closing and while running, and making the buffers failing once after one; a rate set and refused, a notice of the same rate, and a rate of 0; a channel count that changes on its second reading after a rate change; each sample type's smallest, largest and zero values, and one step either side, in both byte orders.

### Playing files

The devices module plays a file, or a program's own source, through a device with a read-ahead on a worker thread, which the audio thread reads through a lock-free buffer without ever waiting on it. When the reader falls behind, playback keeps time, fading to silence for what it lacks and moving on by as much, and says where and how long, so the position always says what was heard. A jump while playing is read ahead at its new place, and playback fades out of the old place and into the new one. Starting and stopping fade over a time of their own, whatever the block size, and a stop ends when its fade does, without the caller waiting. The end comes exactly at the last sample, a loop's join is exact to the sample, a source at another rate plays at the device's through core's resampler, and a new source takes over once the old one has faded out, the old one's frames passed over by the audio thread and let go by the reader. A source that can't be read, as a file on a drive just unplugged, leaves silence where it was to play and says so once each play, tried again as playing goes on, as it may come back; an exception from it never ends the program from the reader's thread.

Tests: a source at the device's rate plays sample for sample, and a mono one on both outputs; a frame the player says is ready plays at once, asked the moment a play starts two thousand times over; a reader held up longer than it reads ahead gives silence for what it lacks, says where it fell and how long, and every frame heard after is the source's at its own place in time; a jump inside a tone never steps further between samples than the fade allows; fades follow the exact curve with blocks of 1 to 4096 frames, and a stop returns at once; files whose lengths are one either side of the block size end exactly at their last frame, and loops of 1 to 513 frames join exactly; a tone at 44.1 kHz plays at 48 kHz within -90 dB of itself; thousands of plays, jumps and stops while blocks play, under the thread and address sanitizers too.

### Measured before it is relied on

A few things no source settles are measured on real devices before the module depends on them: how long a buffer Windows Audio's shared mode gives an input on Windows 10 and 11; whether each system answers a denied microphone with an error or with silence; whether a Mac's built-in microphone and speakers share a clock; whether Core Audio's input and output times already count the safety offset; the shape of a Bluetooth headset's switch of profiles under a running output; and what USB interfaces' ASIO drivers do when unplugged. Measured so far: on Windows 11 25H2, shared mode gives an input the 200 ms of buffer asked for apart from its period, so a thread held up 50 ms every two seconds loses nothing and one held 400 ms loses the excess, and an hour's take kept within 1 part per million of the clock with no runs of exact silence; another program taking an input in exclusive mode ends a shared stream on it with Windows' own reason; a USB interface's driver may offer no raw stream at all; a MacBook's own microphone gives exact silence while its lid is closed; and a USB interface's ASIO driver gives its first blocks in a burst, so its rate is measured from a little after the start. Across a Mac's sleep and a Windows PC's, a stream stops at the system's word that it sleeps and opens its device again once the computer has been awake 3 s; a MacBook with its lid closed sleeps when the hub carrying its displays is unplugged, and its word that it sleeps comes only as it wakes; Windows starts a Bluetooth headset's hands-free input at 16 kHz, the start taking 1.7 s while it connects the call; and every time Windows starts a USB interface's input in shared mode its first 27 packets are exact zeros, 270 ms at 44.1 kHz, unflagged and with their positions running on from the start: the device warming up, kept as it came, since exact zeros can be real, as from a digital input.

## Testing

Unit tests for every module, the plugin validators on every example, and integration tests that open real devices where the runner has them. The devices module is tested against a scripted fake system ([devices](#devices)), its tests passing under the address and thread sanitizers too, on the Mac runner also against BlackHole's loopback devices, a Core Audio server plug-in installed for the run as a test tool alone, so real Core Audio is tested with no hardware, and on real devices by hand before each release: `SYMBOLENGINE_REAL_DEVICES=1` lists the computer's own devices, plays silence through a Mac's built-in speakers and records from its microphone, `SYMBOLENGINE_TEST_OUTPUT` and `SYMBOLENGINE_TEST_INPUT` name devices to play silence through and record from instead, `SYMBOLENGINE_TEST_ASIO` names a PC's ASIO driver to record from, nothing played through it, and `SYMBOLENGINE_TEST_LOOPBACK` names the loopback driver installed, whose devices take signals played to them and give them back, through a Multi-Output device and an aggregate of them too. The host module is tested against a fake format for the layer above the formats, against plugins its tests build themselves to misbehave in every way the [hosting](#hosting) section names, with Steinberg's host checker logging every mistake the host makes, and against free plugins downloaded for each run; a program's own library of plugins is checked by hand before each release. ASIO is built when `SYMBOLENGINE_ASIO_SDK` names the developer's copy of Steinberg's SDK, which the Windows runner fetches for each run, pinned by checksum; a program that ships with ASIO is under Steinberg's licensing agreement, free for a closed-source program, or the SDK's GPLv3. Continuous integration builds and tests on Mac, Windows and Linux on every push, with warnings as errors; on the Mac for Apple Silicon and Intel together, and on Linux a second time with the address and undefined-behavior sanitizers. On each run a project outside SymbolEngine builds against it both ways a project takes it in, by FetchContent and by find_package after installing. Symbol Studio's own checks, run against each release, are the proof that the parts work together in a real product.
